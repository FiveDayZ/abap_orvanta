## 4. 缺陷根因与修复

**根因**（源码级）：`src/tools.ts` 的 `appendTransparentTableRawFields` 把调用方提交的原始行拼进当前行集，而这些行**不含 `DDTEXT`**；`ddicDefinition` 于是渲染出 `description: ""`，`savedDdicResult` 拿这个**请求从未提供过的值**去和 SAP 按数据元素推导出的文本做精确比较，必然不等。

`isSapOwnedDdicText` 救不了它：该规则的放行条件是 `expected.startsWith(actual)`，即「SAP 的值是请求值的**前缀**」（为 R7-E 的描述截断而设）。本例方向相反——请求给的是**空**，SAP 给的是推导值。

**这是三条同族路径中唯一漏掉的一条**：
- `patch_ddic_transparent_table_fields`（`src/tools.ts` L4810-4819）对**改指了数据元素**的字段显式 `delete field.description`；
- `create_ddic_transparent_table`（L4652-4659）构造期望字段时**根本不写 `description`**；
- 只有 append 路径复用了 `ddicDefinition`，把 `""` 写进了期望。

**修复**（`src/tools.ts`）：把期望里**每个被追加字段**的 `description` 删掉，与两条姊妹路径一致；追加字段的其余每个属性、以及被保留的整个布局，仍然精确断言。

**回归测试**（`test/ddic-write-verification-fidelity.test.ts`，+2 条，1409 → 1411）：
- 正例：SAP 为追加字段推导描述时**不得**判失败；
- 反例：某个追加字段的**数据元素**被 SAP 存成别的值时**仍须**失败（证明豁免只限于 `description`，不是整字段豁免）。

**证伪**（按技能库纪律）：把 `dist/src/tools.js` 里该守卫临时改为恒假后单跑该文件 ⇒ **恰好新正例变红**，且逐字复现真机失败信息 `definition.fields[4].description: SAP stored "Derived text for CHAR20" instead of ""`；反例仍通过；其余 4 条不受影响。`dist` 已按字节还原（前后 SHA256 相同）。
