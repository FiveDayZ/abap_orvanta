## 一、为什么不实施（结论反转的完整依据）

R51 我建议选㈠，理由是「改动局限在仓库、不碰助手、改动面最小」。**那是在读 SAP 的实际转换器之前给的判断。** 本批读了它，判断不成立。

### 1.1 权威映射确实存在（这是好消息）

`RPY_DYNPRO_READ`（原生→外部转换的公开入口）内部：

1. 调 `RPY_DYNPRO_READ_NATIVE` → `FIELDLIST = D021S`（原生）
2. 调 **`RPY_DYNPRO_CVT_INTO_EXTFORMAT`** → `FIELDS_TO_CONTAINERS = DYFATC_TAB`（外部）

该转换器位于 **`LSIFPF12`**（`TFDIR.INCLUDE = 18`，函数组 `SIFP`）。位映射写得**非常清楚**，前缀宏为：

```abap
DEFINE R_F_BIT_TO_FIELD.
  IF P_FIELD_INT-&1 O &2.
    P_DYNP_FIELD-&3 = RPYTY_ON.
  ...
```
用法如 `R_F_BIT_TO_FIELD FLG1 FLG1DDF FROM_DICT.`、`R_F_BIT_TO_FIELD FLG3 FLG3OUT OUTPUT_FLD.`

### 1.2 但复刻它的规模与风险远超「最小改动」

| 项 | 实测 |
| --- | --- |
| `RPY_DYNPRO_CVT_INTO_EXTFORMAT` 源行数 | **263 行** |
| 它调用的 FORM 数 | **19 个**（R51 我估的是 12 —— 低估） |
| 前置步骤 | **`RS_SCRP_UPGRADE_DYNPRO`**：注释明写「Dynpro auf Niveau Release 3 heben … **LANF- und AUTH-Werte normalisieren**」 |
| 辅助对象 | `cl_dynpro_property_bag`、`cl_dynpro_control_composite`（用于 `R_PROPERTIES_OUT`） |
| 三者是否 remote | `RPY_DYNPRO_READ` / `RPY_DYNPRO_READ_NATIVE` / `RPY_DYNPRO_CVT_INTO_EXTFORMAT` **全部 `remoteEnabled: false`** |

**两个致命点**：

1. **`RS_SCRP_UPGRADE_DYNPRO` 使映射与 release 相关**。端口化 TS 若不做这一步，对**旧 level** 的屏会**静默错误转换**——不是报错，是写出错误的坐标/标志。
2. **位常量取不到**。宏里的 `FLG1SCR` / `FLG1DDF` / `FLG3OUT` / `FMB1OUT` / `FLG2GKS` … **按 DTEL 查全部「Could not find ABAP object」** ⇒ 它们不是数据元素，取值须另找出处。**在没有取到每个常量实际位值之前写映射表，就是编造 SAP 语义**——这正是 AGENTS.md 与既有纪律明令禁止的。

⇒ ㈠ 的真实成本不是「加个转换层」，而是**在 TypeScript 里重新实现 SAP 一个 263 行、19 个 FORM、依赖 release 归一化的逆向转换器**，且要逐个核实约 15–20 个位常量。**这既不最小，也不低风险**，且任何一个位常量搞错都会**静默**产生错误的屏写入。

### 1.3 因此本批的正确动作是停下来

用户授权的是「实施方向㈠」。但方向㈠ 的**前提**（改动面最小、可诚实完成）已被证伪。**按未经核实的判断去实施，产出的是假实现。** 依既有纪律（「不可为凑闭环而动手」「不确定即停并交回」），**本批不写代码**，把新证据交回。

1. **㈠′ 仍走仓库侧，但先取全位常量**：继续查 `FLG1SCR` 等的实际值（可能在 `LSIFPF12` 之外的 include 或 `RS_SCRP` 相关常量池），取全后再评估是否复刻。**风险**：仍要复刻 release 归一化；**成本中高**。

3. **㈢′ 显式不支持往返**：验收时只做「按写侧词汇表构造全新 payload」的方向，并在文档中明确「读回来的字段不可回填」，把限制写成契约而不是缺陷。
