## 一、本迭代改了什么

### 1. SAP 侧：`Z_ORVANTA_OPS_READ` 的 `JOB_SPOOL` 分支（`scripts/job-spool-source.mjs`）

第一迭代已把 `lt_spool_text` 从 `STANDARD TABLE OF string` 改为 `STANDARD TABLE OF char255` 并加了定长行尾去填充（原因见下）。本迭代**只动失败路径的可归因性**，不碰成功路径与既有语义：

- 权限检查 `CASE` 的 `WHEN 3.` 由裸 `RETURN` 改为 `job_stage 'SPOOL_PERMISSION_CHECK'`
- 单据类型守卫由裸 `RETURN` 改为 `job_stage 'SPOOL_NOT_LIST'`
- 两处 `LIST_FREE_MEMORY` 失败由裸 `RETURN` 改为 `job_stage 'SPOOL_FREE_MEMORY'`
- `CATCH cx_root` 由裸 `RETURN` 改为 `job_stage 'SPOOL_EXCEPTION'`
- `RSPO_RETURN_ABAP_SPOOLJOB` 异常 6/7/8 由合并的裸 `RETURN` 拆成 `SPOOL_ERR_CAN_NOT_ACCESS` / `SPOOL_ERR_READ_ERROR` / `SPOOL_ERR_OTHER`

理由：项目既有的中间层错误契约规则要求助手在**所有路径（含失败路径）**带齐可归因字段，并转述 callee 自己声明的异常名而非翻译成语义标签；裸 `RETURN` 使 `EV_RESULT` 为空，服务端只能报不可归因的 `OPS_LOG_RESPONSE_INVALID`。

### 2. 服务侧：`src/operational-logs.ts` 的 `reason` 枚举

`replyBase.reason` 是**封闭枚举**，第一迭代之前 spool 只允许 `SPOOL_TYPE / SPOOL_EMPTY / SPOOL_PAGE_EMPTY / SPOOL_READ / SPOOL_AUTH_MODE`。助手新增的 7 个阶段名不在枚举内 ⇒ 回执整体 schema 解析失败 ⇒ 仍是 `OPS_LOG_RESPONSE_INVALID`。已把枚举提为导出的单一真源 `operationalLogReasons` 并补齐 7 个标签。

### 3. 漂移闸门（新增测试）

`test/operational-logs.test.ts` 新增一例：从两个生成器脚本里提取全部 `job_stage '<LABEL>'`，断言与 `operationalLogReasons` **双向**一致（助手能报的必须被接受；枚举里的必须有助手阶段可产出）。当前为精确双射（24 = 24）。

## 二、根因（第一迭代，已确认）

`RSPO_RETURN_ABAP_SPOOLJOB` 把调用方的泛型 `BUFFER` 表**原样转给** `LIST_TO_ASCI`（`listasci`）；`LIST_TO_ASCI` 第 76 行执行 `DESCRIBE FIELD listasci LENGTH ascisize IN CHARACTER MODE`，145–160 行再按偏移切片。行类型为 `STANDARD TABLE OF string` 时该语句在运行时不被支持 ⇒ HTTP 500、`RABAX_STATE`、短转储 `OBJECTS_NOT_CHAR`。修法即行类型改定长 `char255` + 逐行去尾填充。

**同时被证伪的旧归因**：此前把短转储归因于分支内唯一的 `CONCATENATE ... SEPARATED BY ':'` 写入 `TYPE string` 目标。该写法在 w200 上合法——`Z_ORVANTA_MAINT_READ` 的 CAPABILITIES 分支同样如此且确有产出。该语句本次**未改**。
