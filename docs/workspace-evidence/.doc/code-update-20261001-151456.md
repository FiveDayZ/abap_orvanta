## 1. 本批改了什么

一处 SAP 助手正文改动（仓库助手），一处静态门强化。

### 1.1 缺陷九：`release_transport_task` 的调用段位错误（定案并修复）

- 对象：`Z_ORVANTA_MCP_DYNPRO_API`（函数组 `ZORVANTA_MCP_CORE`），载体 `ZORVANTA_MCP_DYN228`。
- **纠正的历史结论**：此前四份只读取证与一次内容保持的再激活均未消除短转储，因而把原因判定为「应用服务器加载的接口与仓库声明不一致」，即**平台问题、本服务不可修**。该判定**是错的**。
- 真正根因：`TRINT_RELEASE_REQUEST` 的 `ET_MESSAGES` 声明在**被调方的 `EXPORTING` 段且无 `VALUE(...)`**（即**按引用**）。`CALL FUNCTION` 的段位映射规则是「调用方 `EXPORTING` → 被调方 `IMPORTING`」，只有**按值**的 `EXPORTING` 结果才能由调用方在 `EXPORTING` 段接收。助手把 `ET_MESSAGES` 写在调用方的 `EXPORTING` 段，内核于是到被调方的 `IMPORTING` 参数里按名查找、找不到，**在任何释放逻辑执行之前**抛出短转储 `CALL_FUNCTION_PARM_UNKNOWN`。这一条机制同时解释了此前被当作平台证据的每一点：转储出现在调用点本身而非被调方的具名异常；内容保持再激活永远无效（没有任何东西是陈旧的）。
- 决定性证据取自 SAP 自己的代码，不是论证：
  - `TRINT_RELEASE_REQUEST` 自身第 31-50 行调 `TRINT_RELEASE_WITHOUT_TRANSP` 时，把 `es_request`/`et_deleted_tasks`/`et_messages` 三个**被调方导出**参数全部写在 **`IMPORTING`** 段下；
  - `BAPI_CTREQUEST_RELEASE` 调 `BALW_BAPIRETURN_GET2` 时同样写 `IMPORTING RETURN = RETURN`；
  - 被调方声明原文：`EXPORTING ES_REQUEST TYPE TRWBO_REQUEST / ET_DELETED_TASKS TYPE TRWBO_T_E070 / ET_MESSAGES TYPE CTSGERRMSGS`（全部无 `VALUE(...)`）。
- 修法：把 `et_messages` 由 `EXPORTING` 段移入 **`IMPORTING`** 段。只接收 `ET_MESSAGES`：另两个导出 `TRWBO_REQUEST`/`TRWBO_T_E070` 在本版本**不是 DDIC 对象**（DDIC 复核 not found，见 `.cache/r291`），为它们声明工作区无法通过编译——这一点原注释是对的，故保留。
- 部署：载体 `ZORVANTA_MCP_DYN228` 经人工 SE38+F8 生成并激活；`get_capability_report` 复核 `sourceHash = dbdf80a9782c1776bd862df560fdea120e08323ffe8cf2c41624c5e436b7b7e2`，与导出正文 sha256 逐位一致（部署前后 `interfaceFingerprint` 未动）。

### 1.2 静态门强化：`audit-helper-signatures.mjs` 的自身盲区

原判据把「调用方 `EXPORTING` → 被调方 `IMPORTING` **或** `EXPORTING`」都当作合法，因此**恰好放过了本缺陷**（它报 `problems: 0`）。现改为：被调方 `EXPORTING` 参数若出现在调用方 `EXPORTING` 段，必须声明为 `VALUE(...)`，否则报错并指出应改用 `IMPORTING`；同时新增「调用方 `IMPORTING` 段里的参数必须是被调方 `EXPORTING`/`CHANGING`」的反向检查。

另修一处解析缺陷：这些签名文件是**函数源码的一页**，`EXCEPTIONS` 之后还含被调方自己的 `CALL FUNCTION` 语句，原解析器会继续追加，把形参并集污染（强化判据后立刻产生了一批 `IV_*` 假阳性）。现改为在首个 `EXCEPTIONS` 处终止解析。

**证伪**（`.cache/r294-falsify-audit.mjs`）：把缺陷还原进 canonical 正文的副本后，强化后的门报出唯一一条正是该缺陷；在修好的正文上 `problems: 0`。

## 3. 下一层阻塞的定位（未修完）

沿 SAP 源码逐层追到具体判定点：

1. `TRINT_INTERNAL_RELEASE:178-181` 调 `TRINT_RELEASE_PROJECT_1ST_STEP`（`IV_DIALOG` 透传），返回非零即 `current_message_raising action_aborted_by_user`；
2. 该 FM 只在 `TR_CHECK_PROJECT_LOCKS` 开关为 `'X'` 时调 `TRINT_SHOW_PROJECT_CONFLICTS`，其唯一异常 `USER_CANCELED` 经 `PERFORM ... RAISING release_canceled` 上抛；
3. `TRINT_SHOW_PROJECT_CONFLICTS:94` 调 `TRINT_EDIT_SERIALIZATIONS`，后者的关键分支在 **`TRINT_EDIT_SERIALIZATIONS:111`：`IF iv_dialog = 'X'.`** —— 即该依赖关系编辑**只有带对话框才可完成**；
4. 由此 `USER_CANCELED` → `RELEASE_CANCELED` → `ACTION_ABORTED_BY_USER`，与回执文本「操作已被用户取消」逐字一致。

**关键判别**：`iv_dialog = space` **不是**我们的偏差——SAP 自己的两个可成功调用者（`RSWBO011`、`BAPI_CTREQUEST_RELEASE`）传的也是 `space`/默认值，它们不需要走该对话框分支；而本次目标请求落到了该分支，说明触发条件是**该请求（或其对象）参与了带依赖/串行化检查的 CTS 项目**。

**未能确认的一环（工具边界）**：判定项目归属所需的 `TLOCKP`/`TRDYSERIAL`/`TRSERIAL` **均不在 D5-2 读取白名单内**（实测 `TABLE_NOT_ALLOWED`），因此「本请求是否真的参与项目」无法用现有只读通道取证。这是本次停在判定点的直接原因。
