### 三条实测限制（本次新发现，已写入注释与测试）

1. **`VBHDR` 无 `MANDT`，客户端在 `VBMANDT`** ⇒ 不显式过滤就会返回**所有客户端**的行（与 `TBTCO` 的 `AUTHCKMAN` 同类陷阱）。
2. **失败判据两列都是数值型**（`VBSTATE` 域 `INT1`、`VBRC` 域 `VBRC`/`INT4`）⇒ **可展示、不可作筛选列**。旧读路径的筛选只接受 `C/N/D/T`（`src/table-query.ts:293-301`，拒绝码 `TABLE_QUERY_LEGACY_LAYOUT_UNSUPPORTED`），与 `ALALERTDB` 的 `SEVERITY`/`STATUS` 同类；失败必须在取回的行上按值判断。
3. **`VBCLIINFO` 是字节列**（`RAW`，长度 1）⇒ 旧读路径对字节投影 fail closed（`X` 不在可投影类型白名单内，`src/table-query.ts:304-309`）。定位失败更新不需要它；投影应只取 `VBMANDT/VBKEY/VBUSR/VBREPORT/VBTCODE/VBDATE/VBSTATE/VBRC`。

### 为什么这张表能解 `updates` 族

失败判据写在 `search_failed_updates` 的描述里（`VBSTATE = 253` 或 `VBRC ∈ 2..201`）。那条通道经已批准的 SAP 助手，形状上要求**精确用户名 + ≤1 小时窗口**，158 个已批准窗口因此全部为空。登记 VBHDR 后 `read_abap_table` 可按 `VBMANDT` + `VBDATE` 取一个宽窗口，一次表读即可回答「是否存在失败更新」。
