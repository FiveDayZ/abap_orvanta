## 2. 授权范围内的正文修复（用户裁定 #3）

### 2.1 归因修复：把 JOB 分支的静默退出切开

**根因（Round 17 已定位，本轮修复）**：线上 `job_stage` 宏只在 `lv_body_check='X'`（body-check 模式）与 `lv_diagnostic='X'`（诊断模式）下写 `ev_result`，而 JOB 分支在 `INPUT_VALIDATION`（正文 `:421`）之后**再无任何阶段标记**，直到消息循环。因此该区间内任何裸 `RETURN` 或兜底 `CATCH cx_root. RETURN.` 都留下 `:357` 的默认回执，只报 `INPUT_VALIDATION`，无法定位。

**修复**：在 JOB 分支每处判据**之后**新增 `job_stage`（放在判据之后 ⇒ 回执里的 `reason` 就是「最后通过的那一项」，中止语句是它的下一条）：

| 新阶段 | 位置（判据之后） |
| --- | --- |
| `JOB_SCOPE` | 进入 `JOB_SEARCH`/`JOB_LOG`/`JOB_DETAILS` 分支 |
| `JOB_NAME_VALIDATION` | `iv_jobname`/`iv_program` 校验通过 |
| `JOB_SINGLE_VALIDATION` | 单作业入参校验通过 |
| `JOB_LIMIT_VALIDATION` | `iv_limit` 精确值校验通过 |
| `JOB_HEADER_READ` | `SELECT SINGLE * FROM tbtco` 命中 |
| `JOB_SHOW_AUTHORITY` | `AUTHORITY-CHECK ... 'SHOW'` 通过 |
| `JOB_PROT_AUTHORITY` | `AUTHORITY-CHECK ... 'PROT'` 通过 |
| `JOB_LOG_NAME` | `joblog(6)='JOBLGX'` 校验通过 |

同批把这 8 个名字加入服务端闭集 `operationalLogReasons`（`src/operational-logs.ts`）——该闭集是回执 schema 的一部分，助手能到达而它未列出的阶段会让**整个回执解析失败**（表现为 `OPS_LOG_RESPONSE_INVALID`，掩盖真实结果）。

**行为不变性**：`job_stage` 在正常回执模式下是空操作，故上述改动**不改变任何成功路径的回执**。body-check 模式不受影响：成功路径显式写 `ev_result='OK'`，覆盖中途阶段。

### 2.2 两处 DDIC 分量拼写（首次激活才暴露的既有缺陷）

runtime 分支（`scripts/db-perf-source.mjs`）引用 `SWNCSYSLOAD` 的分量时写成：

```
:217  json_field ',"FIRSTRECDY":"' ls_sysload-firstrecday.   ← JSON 键对，ABAP 分量错
:219  json_field ',"LASTRECDY":"' ls_sysload-lastrecday.    ← 同型
```

首次 `--apply-approved` 在 SAP 侧 `GENERATE` 失败：

```
FUNCTION_SOURCE_ACTIVATION_FAILED: Generation failed:
数据对象 "LS_SYSLOAD" 没有组件 "FIRSTRECDAY"，但具有组件 "FIRSTRECDY"。
```

两处均改为 `firstrecdy`/`lastrecdy`。

**写入未生效**：回执虽标 `outcomeMayBeUnknown: true`，回读证明 SAP **逐字节未变** —— `sourceFingerprint` 仍为 `a6d4b1d2…`，正文中不含 `PERF_SNAPSHOT`/`WP_LIST`/`JOB_SCOPE`/`firstrecday`。激活失败发生在替换之后、提交之前。

### 2.3 新增离线门：DDIC 分量引用静态核对

激活是**写路径上的、一次只报一个**的判据。新增 `.cache/check-ops-ddic-refs.mjs` 把这一类失败挡在部署前：它从 `DATA ... TYPE <struct>` 声明绑定工作区到结构，收集每个 `<var>-<component>` 引用，与 w200 读回的真实分量表比对；结构无缓存时报 `UNCHECKED` 而**不是**通过（缺缓存不得看起来像干净结果）。

```
=== db-perf-source.mjs ===
  DB6PMHSB    ddicFields=17  refs=17  missing=0
  DB6PMHSD    ddicFields=18  refs=18  missing=0
  SWNCSYSLOAD ddicFields=65  refs=40  missing=0
=== runtime-read-source.mjs ===   EPS2FILI 5/5, USRINFO 16/16, WPINFO 25/25
=== operational-log-source.mjs === BTCTL1 4, RSLGENTR_NEW 14, RSLGETYP 3, RSLGFINFO 7, TBTC0 3, TBTCO 14, TBTCP 6, TST01 3
TOTAL missing=0 unchecked=0
```

该门在修复前对 `SWNCSYSLOAD` 报 `missing=1 -> ls_sysload-lastrecday`，即它**确实能失败**。
