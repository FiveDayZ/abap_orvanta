# 修复：共享评审读取器把 RFC 拒答的裸名透出，导致七个调用方各自声明的错误码永不可达

- 时间：2026-09-30 21:50 (+08:00)
- 系统 / 客户端：w200 / 200（SAP ECC，SAP_BASIS 7.31 SP04，DB6，非生产）
- 对象：`abap-mcp-standalone` 服务源码（本地 TypeScript），**SAP 侧零改动**
- 传输：未创建、未修改、未释放任何传输（`GR2K923472` 仍为 `D`）；未部署任何 SAP 对象
- 删除：未删除任何文件或对象

## 一、结论

`src/reviewed-table-reader.ts` 在被调用的 RFC 以 fault 拒答时，抛出的是**被调方自己的裸名**
`NOT_AUTHORIZED` / `RFC_FAILED`；而该读取器的**七个调用方**在各自的 `mapError` 里只映射带自己
前缀的码。结果是这些工具**契约里写明的两个码永远产不出**，任何一次拒答都塌进通用的
`<PREFIX>_QUERY_FAILED`：`read_system_info`、`read_system_parameters`、`read_idoc_status`、
`read_qrfc_queues`、`read_trfc_error_entries`、`read_user_authorizations`、
`read_role_authorizations` 全部如此（`read_user_authorizations` 即操作员本轮点名要修的那一处）。

修法取**单点**：读取器用 `fail()` 把 fault 名挂上调用方自己的码前缀再抛。一处修好全部调用方，
且不再留下"同一条规则在两侧各写一遍"的漂移面。随之删掉上一批在 `read_role_authorizations`
里加的逐调用方兼容分支——读取器改名后那段注释就变成假话了。

| 文件 | 改动 |
| --- | --- |

| `src/role-authorizations.ts` | 删除上一批的裸名兼容分支及其注释（读取器已改名，该分支既冗余又使注释失真） |

## 四、只读复核：`T006` 两行的身份（操作员报告 SE16N 中查无此行）

本批顺带用只读探针 `.cache/r45-t006-identity.mjs`（读数落 `.cache/r45-t006-identity.json`）复核
上一批所依据的两行。**读数与"不存在"不一致**，逐条如下：

| 读法 | 结果 |
| --- | --- |
| `SELECT MANDT, MSEHI, DIMID, ZAEHL, NENNR, ISOCODE, PRIMARY, FAMUNIT FROM T006 WHERE DIMID='TEMP'` | 3 行，**全部 MANDT=200**：`FA` ISOCODE **FAH** 5/9、`GC` ISOCODE **CEL** 1/1、`K` ISOCODE KEL 1/1 |
| `T006A` 文本（MSEHI='GC' / 'FA' / 'K'） | 各 3 条语言行：GC=`°C`、FA=`°F`、K=`K`；`CEL` / `FAH` 作**单位键**不存在（它们是 ISOCODE） |
| `SELECT MANDT, MSEHI, DIMID FROM T006 WHERE MSEHI='GC'`（不含数值列） | 各返回 1 行，MANDT=200 |
| `SELECT ADDKO FROM T006 WHERE MSEHI='GC'`（**单列**，槽在偏移 0） | 仍报 `TABLE_QUERY_NUMERIC_OVERFLOW`；`FA` 同；`K` 正常返回 `0.000000`（8 字符） |
| `SELECT MSEHI, ADDKO ... WHERE MSEHI > 'FA' AND MSEHI < 'GC'` | 6 行全部可解码 |
| `SELECT MSEHI, ADDKO ... WHERE MSEHI > 'GC'` | 215 行全部可解码（含 `TST` = `9.000000`） |
| 全表普查 `SELECT MANDT, MSEHI FROM T006` | **276 行，客户端分布 {200: 276}** |

即：在 **w200 / 客户端 200** 内，`T006` 确有这两行，且 276 行中**只有**这两行的 `ADDKO` 无法解码；
两行分别是摄氏（ISOCODE `CEL`）与华氏（ISOCODE `FAH`、比值 5/9）单位。单列读也被拒，说明问题在
**该字段自身槽内容非十进制**，与字段列表布局无关。

成因（读实现后的判定）：`T006` 含数值列，故该表一律走"对齐读取器" `BBP_RFC_READ_TABLE`
（`src/table-query.ts:322-353` 的切换条件），它按 `DD03L` 的**位数**给 `ADDKO`（`DEC 9/6`）分配
**9** 字符槽，而该字段的十进制文本最多需要 **10** 字符（3 位整数 + 小数点 + 6 位小数）；
装不下时按 SAP 惯例填溢出符，解码守卫据此整行拒绝——守卫的判定正确（绝不放行一个不是值的值）。

**未决**：① 操作员 SE16N 未见到这两行，与本服务三次独立只读读数不一致，需确认 SE16N 所在
**客户端/系统**（w200 客户端 200 之外看不到属正常）；② 该槽的**原始文本**（星号填充还是截断）
在本服务内不可观测——凡投影该列的语句都在产出任何结果前被拒，故"守卫两条子句哪条命中"仍未判定；
③ 是否让读取器在溢出拒绝里带上**行主键与字段名**（可让此类定位不必再做二分，但要改已 verified 工具
的错误面，且需操作员重启 4849 才能取得真机复核）——留待裁定。
