## 根因

同日前两次修复（`char255` 行类型 + 失败路径 `job_stage` 归因、服务端 `reason` 枚举补齐）之后，真实调用仍在服务端被拒。把 `OPS_LOG_RESPONSE_INVALID` 拆成可归因错误（fault / 非字符串 / 超长 / 非 JSON / schema 不符带 issue 路径）后，一次调用即定位到 `spoolId: Invalid`。

- `TSP01-RQIDENT` 的数据元素为 `RSPOID`，域 `RSPOID`：`dataType=INT4`、长度 10（`read_ddic_domain` w200 实测）。
- ABAP 把 `INT4` 赋给 `string` 时**右对齐补前导空格**，因此回执里是 `"spoolId":"     12717"`，不匹配服务端 `src/job-spool.ts` 的 `^0*[1-9]\d*$`。
- 相邻的 `stepNumber` 与 `page` 早已做 `CONDENSE ... NO-GAPS`，唯独 spool id 漏了 —— 这是同一条归一化规则的漏用，而非新契约。

诊断过程中另排除：助手短转储（ST22 仍 9 条、最新 `20260929155932` 属修复前批次，三次调用均无新增）、运行的是旧构建（`dist/src/operational-logs.js` 17:01:14，实例 17:08:59 起于 `dist/src/index.js`）、超时（spool 调用 0.4s、兄弟工具 0.2s）、公共回执层损坏（同实例 `read_background_job_details` 与 `read_background_job_log` 均返回真实数据）、审批指纹（不匹配会报 `OPS_LOG_HELPER_FINGERPRINT_MISMATCH` 而非本码）。
