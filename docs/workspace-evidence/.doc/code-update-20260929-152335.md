## 缺陷根因（本批修的就是它）

2.17 分支把 callee 的异常号**翻译成含义**：`sy-subrc = 1 → no-authority`、`= 2 → not-allowed`、其余非 0 → `TRANSPORT_IMPORT_CHECK_FAILED`（`status failed`），并且**失败路径一行 payload 都不写**。2026-09-29 的 9 次真机调用证明该翻译**双向都错**：

| 观测 | 2.17 的渲染 | 实际是什么 |
| --- | --- | --- |
| 「无法启动传输控制程序 tp」 | `not-allowed`（判定） | 环境/接口层条件 |
| 「针对请求 X 的导入已经运行」 | `TRANSPORT_IMPORT_CHECK_FAILED`（失败） | callee 的拒绝 |

且同一请求 `GR2K918001` 于 14:51 得 `not-allowed`、14:53 起得 `CHECK_FAILED`（`AAAK000001` 亦然）⇒ 回复随时间变化；失败路径下 `transportNumber`/`verdict`/`localE070Status` 全空 ⇒ 不可归因。

## 助手侧改动（`scripts/bootstrap-sap-helper.ps1`）

- 能力表：`INSPECT_TRANSPORT_IMPORT|2.17|R` → **`|2.18|R`**（`PROTOCOL|MAX` 由表派生，随之为 2.18）。
- 新增声明：`DATA lv_tr_import_verdict TYPE string.`
- 分支（现 L12972..13099，128 行）：
  - `CASE lv_tr_import_subrc.` 把子返回码映射为**callee 自己的异常名**：`0 → importable`、`1 → permission_denied`、`2 → import_not_allowed`、`3 → enqueue_failed`、`4 → tp_call_failed`、`5 → tp_interface_error`、`6 → tp_reported_error`、`7 → tp_reported_info`、`WHEN OTHERS → unknown`。**不再输出 `no-authority` / `not-allowed` 这类服务侧推断的语义。**
  - 新增 payload 行 **`CALLEE_SUBRC`**（`WRITE ... LEFT-JUSTIFIED` 到 char4）。
  - **所有路径**都写同样的行：`TRKORR` / `SIMULATE_MODE` / `CALLEE_SUBRC` / `IMPORTABLE` / `VERDICT` / `LOCAL_E070_STATUS` / `MESSAGE`。
  - 声明内异常（1..7）**一律**走 `ev_status = 'S'` + `TRANSPORT_IMPORT_CHECKED` —— callee 的异常就是「答案」；只有**未声明**异常（99）才是故障，走 `TRANSPORT_IMPORT_CHECK_FAILED`，**并且仍带上述全部行**。
  - 所有 `ev_version` 改为 `'2.18'`。
- 分支上方注释同步改写：删除「exits before the tp call / tp is never started」这类**未被观测支持**的说法，改为只声明结构性事实（接口不携带系统名与模拟模式）。

## 剩余风险

1. `helperMessage` 来自 `sy-msg*`，而 `CALL FUNCTION ... EXCEPTIONS` 不清 `sy-msgid`：若 callee 抛出**不带消息**的异常，理论上可能渲染上一次调用遗留的文本。本代码库既有分支（L12025 / L12214 / L12860 等）用的是同一模式、且无一处 `CLEAR sy-msg*`，本批沿用同一约定未引入新写法；`calleeSubrc` 是权威判别字段。
2. `verdict` 的**语义**（哪个名字意味着拒绝、哪个意味着故障）仍由 callee 自己定义，本工具只如实转述、不解释；`enqueue_failed` 这种「读起来像故障」的名字出现在拒绝场景即为实例。
3. 「模拟模式是否真的不启动 tp」仍未定论（callee 消息提到 tp），只读通道无法取证。
