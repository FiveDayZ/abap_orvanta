## 2. 前置阻塞的解除（SAP 账号锁定）

本轮先解除了一个**由本工作流自身造成**的阻塞，过程记录如下，供后续避免重演。

- 现象：4848 连续多次返回 `SAP_LOGON_REJECTED`（HTTP 401），重启无效。
- 根因（源码确证）：`src/adt-backend.ts:1814-1817` 每次建立连接固定发**两次**登录（`client.login()` + `client.statelessClone.login()`）；`:1822-1824` 登录失败即从缓存删除，故**每次工具调用都重新登录一次**。本轮密集调用 `get_sap_system_info` / `diagnose_sap_failure` / `get_capability_report`（后者逐个探测 5 个 helper），**失败登录计数被累计，触发 SAP 账号锁定**。
- 另一处误导：`.cache/start-repo-4848.ps1:37` 仅在 `ABAP_MCP_W200_PASSWORD` 于当前进程「未设置」时才 `Read-Host` 提问；启动窗口若残留同名变量，脚本静默使用旧值启动，表现为「重启多次但症状完全一致」。
- 处置：Basis 解锁 `wys` → 干净窗口清除变量 → 重启 4848 并输入有效口令 → `get_sap_system_info` 返回 `status: ok`（ECC / 731 / 内核 720 / DB6 / 客户端 200）。
- 纪律固化：**登录类故障排查禁止密集试错**；解锁后只发**一次**验证调用，通过后再一次性跑完取证。

## 3. 本轮修复的缺陷：扫描器分类器把成功答复判为失败

### 3.1 缺陷

`scripts/probe-ops-read-sweep.mjs` 的 `classify()` 用**错误码子串**判定结果：

```js
if (/_FUNCTION_UNVERIFIED|_RFC_FAILED|_RESPONSE_INVALID|_CALL_FAILED|_QUERY_FAILED/.test(text)) {
  return "failed"
}
```

而本 release 的原生数据预览端点**必然失败**已是既知事实，工具会记录该原生尝试的 `nativeCode: "SAP_DATA_QUERY_RESPONSE_INVALID"`，随后**成功回退**到 `rfc_read_table` 并正常作答。子串规则因此命中**已恢复的中间步骤**，把 `status: "ok"` / `"partial"` 的答复误判为 `failed`。

**首轮（ops-n1b）实测影响**：8 个工具中 4 个被误判 —— `read_system_parameters`(`partial`)、`read_qrfc_queues`(`ok`)、`read_idoc_status`(`ok`)、`read_user_authorizations`(`partial`)，全部因告警文本含 `_RESPONSE_INVALID` 被判 `failed`。

### 3.2 反向风险（更危险，已一并消除）

`read_work_processes` / `read_user_sessions` 答复为 `status: "unavailable"`（RFC 返回空），却带 `RUNTIME_RESOURCES_RESPONSE_EMPTY` 告警。若只按「含 `_RESPONSE_EMPTY` 即 empty」处理，会把**未发生的读取**当成「空但健康的正例」，进而提议登记为 `verified` —— 这正是要防的假阳性。

### 3.3 修法

判定改为**以答复自身的 `status` 为准**，仅在读不到 status 时才回退到错误码，且回退时剔除良性原生码：

| 答复 `status` | 判定 |
| --- | --- |
| `empty` | `empty` |
| `ok` / `partial` | `answered`（`partial` 仅表示行数被截断，读取确实发生） |
| `unavailable` | `failed`（服务明说读取未发生） |
| 无 status | 回退错误码，并先剔除 `SAP_DATA_QUERY_RESPONSE_INVALID` |

另：`isError` 与 `*_NOT_AUTHORIZED` / `TABLE_NOT_ALLOWED` 仍优先判 `refused`（权限与平台边界）。

### 3.4 验证

对 ops-n1b 已捕获的 8 份原始答复重跑新分类器，**8/8 与各自 `status` 一致**：

```
read_work_processes       status=unavailable => failed    OK
read_user_sessions        status=unavailable => failed    OK
read_workload_directory   status=ok          => answered  OK
read_system_parameters    status=partial     => answered  OK
read_qrfc_queues          status=ok          => answered  OK
read_idoc_status          status=ok          => answered  OK
read_user_authorizations  status=partial     => answered  OK
read_file_system_directory status=unavailable => failed   OK
```

复核脚本：`.cache/n1b-reclassify.mjs`（一次性比对，非测试）。

| 工具 | 判定 | 数据源 | 实得 |
| --- | --- | --- | --- |

| `read_system_parameters` | **verified** | `TPFYPROPTY` + `TPFHT` | 50 参数 + 14 profile（截断） |
| `read_qrfc_queues` | **verified** | `TRFCQOUT` + `TRFCQIN` | `ok`，0/0/0 |
| `read_idoc_status` | **verified** | `EDIDC` + `EDIDS` | `ok`，8 条控制记录 |
| `read_user_authorizations` | **verified** | `AGR_USERS` + `AGR_TCODES` + `UST04` | 50 角色分配（截断） |
| `read_work_processes` | failed | `TH_WPINFO`（SOAP-RFC） | `TH_WPINFO: RUNTIME_RESOURCES_RESPONSE_EMPTY` |
| `read_user_sessions` | failed | `TH_USER_LIST`（SOAP-RFC） | `TH_USER_LIST: RUNTIME_RESOURCES_RESPONSE_EMPTY` |
| `read_file_system_directory` | failed | `EPS2_GET_DIRECTORY_LISTING` | `..._RUNTIME_RESOURCES_RFC_FAILED` |

**三个失败的同源性（2026-09-27 补测，逐工具定性）**：三者根因**不同**，不可合并为一句"平台不支持"。

| 工具 | `includeExecutionSupport` | 服务端给出的原因 |
| --- | --- | --- |
| `read_work_processes` | **false** | `TH_WPINFO`：`WITH_CPU` 的数据元素不是已验证的基本类型；`WITH_MTX_INFO`、`MAX_ELEMS` 的 DDIC 对象不存在（`DDIC_OBJECT_NOT_FOUND`） |
| `read_user_sessions` | **false** | `TH_USER_LIST`：`LIST` 输出含 `MSHOSTADR`，类型未验证 |
| `read_file_system_directory` | **true** | 接口与类型**均通过验证**，故障发生在**运行时 RFC 调用**（`RUNTIME_RESOURCES_RFC_FAILED`）——与上两者不同类 |

复现命令（只读）：

```powershell
node .cache/mcp-call.mjs read_function_module_interface '{"connectionId":"w200","functionName":"TH_WPINFO","includeExecutionSupport":true}'
```

**一个必须写明的区分**：`includeExecutionSupport=false` **不等于**「工具定义已过期」。2026-09-27 实测 `TH_WPINFO` 的
双指纹与 `src/runtime-resources.ts` 中钉死值**逐位相同**（`sourceFingerprint` `cf3be4d6…`、
`interfaceFingerprint` `e5d7078c…`），故工具自身的定义守卫（`reviewedWorkProcessDefinition`）**通过**，
失败发生在之后的实际调用路径。两道门不是同一道门。

**零行 ≠ 空答案（设计使然）**：`collectWorkProcesses` / `collectUserSessions` 在 `!rows.length` 时抛
`_RESPONSE_EMPTY` 并将状态置 `unavailable`，理由是运行中的系统**不可能**真的没有工作进程或会话 ⇒ 零行说明
读取未真正生效。与此相对，`SWNC_GET_WORKLOAD_DIRECTORY` 允许空目录（采集器目录本可为空），故同样
`returnedCount: 0` 时它报 `status: "ok"`。**这一差异是有意的，不是不一致。**

**登记结果**：三者一律保留 `unverified`（**不是** `failed`，也不是 `platform-unsupported`）——按
`test/verification-registry.test.ts` 的契约，`unverified` 条目**不得**携带 `evidence` 或 `lastAttemptAt`
（"未验证"不得悄悄变成"它在 T 时刻跑过"），因此失败观察只写在 `notes` 与本记录中，不占用证据字段。

**5 个转 `verified` 的条目**：`availabilityBasis` 取 `target-specific`（这些工具 `helper: null`，
按契约只能取 `native-adt` 或 `target-specific`，不得取 `runtime-observed`）；证据指向本记录
（`.doc/code-update-20260927-084500.md`），原始答复留在 `.cache/evidence-ops-n1c/`。
