## 2. 代码改动（仓库侧，无 SAP 对象变更）

### 2.1 新增观测分支

文件：`abap-mcp-standalone/src/write-prechange-evidence.ts`

在 `release_transport_task` 分支之后、`run_abap_program` 分支之前新增一支，覆盖 `release_background_job` 与 `cancel_background_job`：

- **观测源**：目标作业自己的 `TBTCO` 行，键为 `JOBNAME` + `JOBCOUNT`。选它是因为该行的 `STATUS` 正是写操作要改变的那个字段。
- **读取通道**：走共享的、带指纹门禁的 `createReviewedTableReader`，而**不是** SM37 作业工具（`read_background_job_details`）。理由是可验证的：助手作业详情分支在 `SDLSTRTDT` 为空时由 `make_time` 宏 `RETURN` 掉整个函数模块，而这恰是「已计划、从未启动」的作业——正是 release 存在的意义所在，用它会拒绝掉这两个工具本来要处理的每一个作业。`TBTCO` 在交付白名单内（`src/table-allowlist.ts`）。
- **字段**：`JOBNAME, JOBCOUNT, STATUS, SDLSTRTDT, SDLSTRTTM, SDLUNAME, AUTHCKMAN, LASTCHDATE, LASTCHTIME`；`maximum: 1`；`codePrefix: "JOB_OBSERVATION_"`。
- **三态语义**（不把「读失败」误记成「不存在」）：
  - 读到行 ⇒ `exists = true`，`version = STATUS`，`fingerprint = hashWriteInput(JSON.stringify(row))`；
  - 读到空集 ⇒ `exists = false`，附解释性告警（助手会重读作业头并答 `JOB_NOT_FOUND`，不会动一个它没读到的作业）；
  - 读取本身失败 ⇒ `exists` **保持 `null`**，闸门照旧在接触 SAP 前拒绝，而不是把作业报成已消失。
- `evidence.active = null`：作业行没有「活动/非活动」语义，与 `release_transport_task`、`delete_sap_lock` 两支保持一致。

未触碰 `sourceObject()`：新分支位于 if/else 链的兜底分支之前，`observeSourceTarget()` 对这两个工具已不可达。

### 4.3 失败根因（SAP 自身源码证明，非推断）

`JOB_RELEASE_FAILED` 是助手 `JOB_RELEASE` 分支对 `BP_JOB_RELEASE` 除 7（无权限）、9（作业不存在）、10（无步骤）之外所有异常的兜底码。逐个排除：

- 作业存在且 `STATUS='P'` ⇒ 排除异常 1/2/9，且已通过助手的 `<>'P' AND <>'S'` 前置判据；
- `TBTCP` 中存在 `ZTEST0018/16413100` 的步骤 1（程序 `ZTEST0018`）⇒ 排除异常 10；
- 余下最有嫌疑的是异常 3 `missing_start_date`。

直接读 SAP 标准源码验证（`search_abap_object_lines`，对象 `BP_JOB_RELEASE`，w200，只读），第 61-66 行：

```abap
* 4. check start data / time
    IF job_entry-sdlstrtdt EQ space OR
       job_entry-sdlstrttm EQ space.
      MESSAGE e653 RAISING missing_start_date.
    ENDIF.
```

而该作业的 `TBTCO-SDLSTRTDT` 与 `SDLSTRTTM` **都是空**。

**并且这不是这一个作业的问题**：`TBTCO` 中 `STATUS='P'` 的行全系统只有 3 条——`SWEQSRV/18082300`、`ZTEST0018/16413100`、`ZTEST0018/16413400`——**三条的 `SDLSTRTDT`/`SDLSTRTTM` 全部为空**（`.doc/r24-tbtco-p-jobs.json`）。因此在这台系统上没有任何作业能被 `BP_JOB_RELEASE` 释放；要让 `release_background_job` 取得真机验收，必须先存在一个带启动日期的 `'P'` 作业，而创建作业正是 `jobs` 族尚未建成的那部分能力（`create_background_job`）。

**这是目标数据条件，不是工具缺陷**：工具正确地读取了作业、正确地报告了 SAP 自己给出的具名失败，并且没有把失败渲染成成功。
