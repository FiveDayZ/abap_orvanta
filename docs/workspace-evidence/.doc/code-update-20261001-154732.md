## 2. 缺陷十：`iv_as_background_job = 'X'`（本批新定案）

**机制**（读 SAP 源码定案）：`FORM choose_execution_mode`（`LSCTS_RELEASEF13:848`）开头即

```abap
IF pv_as_background_job = 'X'.
  IF NOT ps_request-h-trfunction CA sctsc_types_tasks
  AND NOT ( ps_request-h-trfunction = sctsc_type_customizing ... ).
    PERFORM project_release_1st_step   USING pv_dialog ps_request.
  ENDIF.
  MESSAGE e653(tk) RAISING release_in_bg_mode.      " ← 在此停下
ENDIF.
CHECK pv_dialog = 'X'.
```

该标志的语义**不是**「无 GUI 释放」，而是**「跑完前置检查后把释放交回调用方去排后台作业」**。负责排该作业的 wrapper 是对话框事务 `TR_RELEASE_REQUEST`；RFC 调用方没有它，因此被调方永远停在 `MESSAGE e653(tk) RAISING release_in_bg_mode`，释放从未发生。

**决定性对照**：SAP 自己两个可成功调用者**都不设**该标志——`RSWBO011` 传 `iv_dialog = ' '` 且不传该参数；`BAPI_CTREQUEST_RELEASE` 传 `iv_dialog = space`、`iv_without_objects_check = 'X'`、`iv_without_docu = 'X'`，同样不传该参数（取默认 `' '`）。

**为何此前一步结论是错的（自我更正）**：上一轮用「新建一个不属 CTS 项目的请求」验证项目归属假设，结果**同样**以 `TRANSPORT_RELEASE_FAILED` / 「操作已被用户取消」失败，当时据此把原因归到项目串行化检查。实际上 `iv_as_background_job = 'X'` 的分支在**任何项目逻辑之前**就返回，所以两种请求必然同样失败——该实验**无法**区分这两者，结论不成立。真正区分它们的是本次读到的 `choose_execution_mode` 源码。

**修法**：移除 `iv_as_background_job = 'X'`，让其取被调方默认 `' '`（与 SAP 自身调用者一致）。同时复核 `iv_dialog = space` **保留**：它与 SAP 自身调用者一致，且 `check_documentation` 只在 `pv_dialog = 'X'` 时才查文档，传 space 使其不做无对话框无法完成的交互。

**载体生成守卫的处理**：`generate-repository-carrier.mjs` 拒绝生成，因为「SAP 侧存在而仓库没有的一行」正是它要防的漏修类型。该守卫是对的，因此**没有**用 `--accept-live-differences` 绕过，而是把这次删除登记进脚本的 reviewed-removal 列表（`REVIEWED_REMOVED_LINES`）并写明理由，使守卫仍能区分「有意删除」与「丢失的修复」。

## 4. 剩余阻塞：环境边界（非本服务可修）

`TRANSPORT_EXPORT_FAILED` + 「无法启动传输控制程序 tp」与**同族 import 工具已记录的边界完全一致**（`docs/ops-coverage.md` §7.24 D）：SAP 自己的 `TMS_TP_IMPORT` 在本系统返回 `calleeSubrc 2` 与同一句文本、`importable false`，即 **tp 在本系统起不来**（环境/TMS 边界），与请求是否已释放无关。

本次试图进一步取证「缺什么」受限：`TCESYST`/`TMSCSYS`（目标系统与路径表）**不在 D5-2 白名单**（`TABLE_NOT_ALLOWED`），`read_system_parameters` 也未返回传输目录参数。故「tp 二进制、`DIR_TRANS`、还是到 GR3 的路由」这一层无法只读区分——这是工具的取证边界，如实记录。

**重要**：三步失败均为**安全失败**——`E070` 三个请求状态始终为 `D`，无不可逆效果。
