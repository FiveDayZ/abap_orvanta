## 最小交付

1. 准备严格限定工具、函数、连接、业务键、字段、容器、调用次数的验收驱动。先做可独立完成的本地范围守卫、原生契约解析和拒绝/未知结果回执测试；不能以本地 mock 声称 SAP 原生拒绝或回滚已通过。
2. 定义无改值的 native stale 案例：保留当前 MSEHL，以错误 expected version 触发锁内版本拒绝。预期 TEXT_VERSION_CHANGED / committed=false；调用后通过 r35 对账核对完整行、CTS 投影和获准定向锁。该函数是写入口，即使预期拒绝，也必须取得该具体 native 调用范围授权后执行。
3. 定义真实 CTS 拒绝案例：只读选择已存在且不适用的容器，不为了测试释放 429/430、不生成伪状态。预期先拒绝且值/目标 CTS 不变化，首根因保留。r32 已有 Workbench 类型拒绝不重复计为新覆盖；如没有安全可用容器，此案例保持待条件。
4. 准备并发契约但不执行：若另获批准，在同一新鲜完整版本上发送至多两条具名命令，仅使用 KG/ZH MSEHL、429/430。预期至多一条实际生效，另一条因锁/版本拒绝；从独立新鲜读回制定一次恢复，不使用旧恢复版本、不盲重试。出现未知结果先只读对账，停止后续写命令。
5. 准备 API/CTS 故障与 rollback 验收矩阵。必须具备目标系统真实、可控且获批准的故障条件，例如独立测试键或受限测试用户；不得添加任意生产故障开关、修改 SAP 标准源码或故意破坏现有 CTS。没有条件时明确保留未验收，不能把静态 ROLLBACK WORK 或 mock 当真实 rollback 证据。
6. 明确 r35 可选锁查询正例的既有审批依赖，并准备共享服务集成清单：核对并行差异、保留原回执状态根、冻结构建、确认使用者实际版本。共享服务本轮未重启；部署与实际服务验收单独执行。

## 验收条件

| 范围 | 通过所需证据 |
| --- | --- |
| 本地实现 | 受限 schema/调用范围守卫、真实 MCP 调用契约、未知回执保留及相关回归；源码与运行快照逐项一致 |
| native stale | 真实 SAP 首根因及 committed 标识；完整行/版本前后一致；有界 CTS 对账一致；获准定向锁无残留或说明具体不可用 |
| CTS 拒绝 | 当前源/接口及真实容器元数据；拒绝发生在维护之前；无值变化/额外目标 CTS；原始回执保留 |
| 并发 | 仅已批准两条命令的原始回执、时间、版本、最终完整行、CTS 目标计数与恢复闭环；不得把无改值重复调用称为并发冲突验证 |
| 故障/回滚 | 真实首根因、提交状态、完整持久化效果、CTS 与锁残留；不明结果保持 unknown 并交由对账；不能宣称通用原子 rollback |
| 交付 | 唯一开发记录、正/负例证据、适用检查结果、剩余限制与下一阶段计划 |
