## 1. 根因（已确认）

`Z_ORVANTA_MAINT_READ` 1.1 正文的 `ARCHIVE_STATUS` 分支调用 `ARCHIVE_ADMIN_SELECT_SESSIONS`，其导出 `ARCH_T_RUNS` 携带结构 `ARCH_RUN`。载体在 SAP 内 `GENERATE` 报：

```
ERROR: GENERATE failed: 数据对象 "LS_ARCHIVE_RUN" 没有名为 "USER_NAME" 的组件。
body line: 450 word: LS_ARCHIVE_RUN-USER_NAME
```

**不是正文缺陷，而是目标系统上编译器视图与 DDIC 视图不一致**：

| 视角 | 事实 |
| --- | --- |
| DDIC | `DD02L` 1 行活动记录（`TABCLASS=INTTAB`、`AS4LOCAL=A`、`AS4VERS=0000`）；`DD03L AS4LOCAL='A'` 39 个活动字段；`AS4LOCAL='N'` 查询 0 行（无未激活版本） |
| ADT | `read_ddic_structure(ARCH_RUN)` 返回同样的 39 字段（`version=20110901132545`，包 `SARC`） |
| **编译器** | **只认深层组件 `ADMI_RUN`**；其余 25 个字段一律报「没有名为 X 的组件」（错误表上限 26 条，`ARCHIVE_FILES`/`ST_WRI_JOB` 未出现在错误里可证） |

两条**独立编译路径**结论一致：R03 载体的 `GENERATE`，以及干净探针程序 `ZORVANTA_PROBE_KIND_01` / `_ROUTES_01` / `_COMPARE_01`（`create_object_programmatically` 会做完整语法检查与激活，可作编译判据）。`ARCH_RUN` 在数据元素、域、表类型三个命名空间均不存在，透明表查询报 `OBJECT_TYPE_MISMATCH`。

## 2. 修法（路线 A：改用透明表）

`ADMI_RUN` 为**透明表**（包 `SARC`，`version=20110901130942`，主键**仅 `DOCUMENT`**，`CLIENT` 非键字段 ⇒ 表本身不分客户端），字段齐全（25 个：CLIENT、COMMENTS、CREAT_DATE、CREAT_TIME、DELETE_FLG、DOCUMENT、OBJECT、STATUS、SYSID、USER_NAME、INTERRUPTD、NOTGUILTY、…）。编译证明：探针程序 `ZORVANTA_PROBE_ARCHIVE_SEL_01` 以 `TYPE STANDARD TABLE OF admi_run` + `SELECT … INTO CORRESPONDING FIELDS OF TABLE … UP TO n ROWS` + `SELECT COUNT(*) FROM admi_files` **创建并激活成功**。

正文改动（`scripts/maintenance-diagnostic-source.mjs`）：

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 工作区/内表类型 | `TYPE arch_t_runs` / `TYPE arch_run` | `TYPE STANDARD TABLE OF admi_run` / `TYPE admi_run` |
| 数据源 | `CALL FUNCTION 'ARCHIVE_ADMIN_SELECT_SESSIONS'`（12 个状态开关全置 `'X'`） | `SELECT document object status client user_name sysid comments creat_date creat_time FROM admi_run … ORDER BY document ASCENDING` |
| 客户端语义 | 选择器 `CLIENT_DEPENDENCE = 'X'` | 显式 `WHERE client = sy-mandt`（表不分客户端，条件必须显式） |
| 行上限 | `DESCRIBE TABLE … LINES` + `> 2000` ⇒ `LIMIT_EXCEEDED` | `lv_fetch = lv_limit + 1` + `UP TO lv_fetch ROWS`，越界即 `hasMore`（与其它分支同一先例） |
| 用户过滤 | `LOOP` 内 `CONTINUE` 后过滤 | `lt_rng_user` 条件下推进 `SELECT`（否则截断前过滤会少行并误报 `hasMore`） |
| 文件数 | `DESCRIBE TABLE ls_archive_run-archive_files LINES` | 逐会话 `SELECT COUNT(*) FROM admi_files WHERE document = …` |
| 清理 | `CLEAR: lt_archive_runs, …` | `REFRESH lt_archive_runs.`（`CLEAR` 对 `STANDARD TABLE OF <结构>` 是非法操作数） |
| 离线断言 | `assertSortTargetsAreStandardTables` | 追加 `assertAdkArchiveStructuresAreNotTyped`（正文不得以 `ARCH_RUN`/`ARCH_T_RUNS` 为类型） |

**JSON 键未变**（`document/object/status/client/username/systemId/createdSystemTime/comments/fileCount` + `hasMore`），服务侧契约与 schema 未改。

### 语义差异（必须记录，不可静默丢弃）

1. **状态语义**：原先"所有状态 heading 始终显式请求"（因为选择器在状态集为空时 `EXIT`，空调用返回 0 会话）；现在不再有状态过滤，**每个已记录状态码都可命中**，`status` 返回 `ADMI_STRUN` 原始码而非 ADK 的显示文本/分组。服务侧 `statusSelection` 文案与 `contracts.ts` 描述已同批改写。
2. **授权检查**：直读表**绕过了 ADK 选择器内置的 `AUTHORITY-CHECK`**（`S_ADMI_FCD` / `S_ARCH_*`）。读范围受本机批准文件（`SARA` 源）与服务端 `readOnly` 契约约束，但不再有 SAP 侧 ADK 授权检查。
3. **上限**：单次上限由 2000 行改为服务侧 `maxResults`（≤100）+ `hasMore`。

## 6. 本轮发现的新缺陷（未修，待裁定）

`execute_data_query` 在 w200 上**拒绝一切 `COUNT` 聚合**，且报错自相矛盾：

```
TABLE_QUERY_AGGREGATE_UNSUPPORTED: COUNT is not translated.
Supported aggregates are COUNT, SUM, MIN, MAX; AVG is not among them …
```

在**白名单内**的 `DD03L` 上同样复现（`COUNT(*)` 与 `COUNT(FIELDNAME)` 皆然）⇒ 与表无关，属服务侧回退方言的聚合翻译缺陷（或该错误文案的枚举本身错误）。影响：任何"先计数再取样"的诊断路径不可用。未改动，留待用户裁定。
