### 3.2 update —— 未达成功路径

同一对象、同一 `expectedFingerprint`，连续 3 次真调用，全部被**助手**（非本地守卫）拒绝：

```
status E / code ENHANCEMENT_INACTIVE_VERSION_EXISTS / "Resolve inactive version before update"
```

- `src/tools.ts` 的本地守卫检查 `definition.hasInactiveVersion`；该对象的**四次读回**（含每次被拒调用自身 `sapPreChangeEvidence` 里的那次）一律 `hasInactiveVersion / hasSavedInactiveVersion / hasUnsavedInactiveVersion` 全 false。
- 助手 `UPDATE_HOOK_ENHANCEMENT` 分支的顺序是：`cl_enh_factory=>get_enhancement( ... lock = 'X' bypassing_buffer = 'X' )` → **然后才** `li_enh_object->has_inactive_version( )` → 为 `'X'` 即 `unlock` 并拒绝。
- 读路径 `READ_ENHANCEMENT_IMPL` 发的是**同一个调用但不带 `lock`**，从不报有非活动版本。
- **判别性探针**：`manage_enhancement_implementation_state(action=activate)` 用的是**完全相同的加锁读**，它回 `ENHANCEMENT_IMPLEMENTATION_ACTIVATED` —— 即加锁读同样看到「有非活动版本」；且其 `previousFingerprint` 与探针后读回的指纹相同，说明它激活的那份与活动版本内容一致。紧接着再发一次 update 仍被同一码拒绝。
- 因此**判据指向：加锁本身物化了非活动版本，而 update 分支在加锁之后才检查该标志，守卫在自己的锁所造出的状态下必然触发**。此结论由测量支持，但未证到最后一环；**能结案的做法**是在取锁之前求值该标志（或改用不加锁的读），重新部署后复跑。
- 每次拒绝都是安全失败：对象指纹与源码三次前后逐字不变；SM12 `entries: []`；`list_write_recovery_operations` `count: 0`；助手在 `modify_hook_impl` 之前返回，未派发写入（`sapInvocationStarted: true` 指的是已发生的那次读）。

## 6. 跳过项与剩余风险

**跳过（附具体原因）**

- `create` 的 `ENHANCEMENT_IMPLEMENTATION_ALREADY_EXISTS` 拒绝路径：需二次创建同名对象，不在一次性授权内。
- `HOOK_CREATE_INPUT_REQUIRED`、隐式增强点、`originalObjectType` 的 `CLAS`/`PROG` 变体：未构造目标。
- `update` 的成功路径：被助手守卫阻断，无法到达。
- `delete` 的 `ENHANCEMENT_IMPLEMENTATION_STALE_FINGERPRINT`、`PACKAGE_MISMATCH`、`ENHANCEMENT_DELETE_FAILED`：未构造输入。
- `description` 的 36 字符上限未做端到端二次确认（本批只观测到截断现象）。

**剩余风险与优先级**

1. **高**：`update_enhancement_hook_implementation` 在任何对象上都可能被同一守卫阻断；`UPDATE_BADI_ENHANCEMENT` 与该分支共用同一段守卫代码，**R18 的 `update_new_badi_implementation` 预计撞同一面墙**，排期时应先取判据再投入。
2. **中**：`delete_enhancement_implementation` 留下 TADIR 残留且不可自愈，调用方需要人工清理入口（已在上文点名）。
3. **低**：DYNPRO 助手的 `IV_DESCRIPTION` 仍为 CHAR 36，与契约声明的 255 不一致；若要改型，属接口参数表变更，须走人工 SE38 + F8 载具路线。

**边界确认**：本批**未修改任何 SAP 标准对象**、**未释放任何传输**、**未部署任何 SAP 助手**、**未请求或记录任何 SAP 凭证**；未执行清理性删除（残留一律只报告）。
