## 1. 变更内容

### 1.1 被证伪的静态声明（4 处，同批修正）

R13 实测证明 DDIC 助手的 `IV_DESCRIPTION` 有效上限是 **36 字符**，而四个工具契约把上限写成 **60 字符**。这类声明在「调用方按声明送 60 字符、实际只存 36 字符且回执成功」的方向上是假话：

| 工具 | 被证伪的原文 | 修正后 |
| --- | --- | --- |
| `upsert_search_help` | `description is limited to 60 characters, the same as every other DDIC object.` | 明确 `DD30V-DDTEXT` 为 60 宽但助手形参 `TSTCT-TTEXT` 为 CHAR 36，超长在 RFC 边界截断且写入仍成功 |
| `upsert_lock_object` | 同上 | 同上（`DD25V-DDTEXT`） |
| `upsert_number_range_object` | `description is the long text of the helper logon language (TNROT-TXT, 60 characters).` | 补 `TNROT-TXT` 60 宽、形参 CHAR 36、截断行为 |
| `upsert_maintenance_view` | `description is DD25V-DDTEXT (60 characters).` | 补形参 CHAR 36 与截断行为 |

### 1.3 上限数字收归单一出处

`src/helper-operation-limits.ts` 新增：

- `DESCRIPTION_PARAMETER_TYPE_LENGTHS = { "TSTCT-TTEXT": 36 }` —— DDIC 类型 → 长度

`src/contracts.ts` 的 `ddicHelperDescription` 文案由 `HELPER_DESCRIPTION_PARAMETER` 插值生成，数字不再散落。选择 `helper-operation-limits.ts` 是因为该模块**已有同类先例**：`IV_OPERATION` 的「DDIC 类型 → 长度」表 `OPERATION_PARAMETER_TYPE_LENGTHS` 与生成器交叉校验。`pre-sap-validation.ts` 无任何 import，故 `contracts.ts → helper-operation-limits.js` 不构成循环依赖。

### 1.4 守卫测试（+1，1408 → 1409）

`test/helper-operation-limits.test.ts` 新增一条，做三件事：

1. 从**生成器源码**读回 `IV_DESCRIPTION` 声明的 DDIC 类型，断言与 `HELPER_DESCRIPTION_PARAMETER.ddicType` 一致（类型锚在外部真值上）；
2. 断言 `HELPER_DESCRIPTION_PARAMETER.length === DESCRIPTION_PARAMETER_TYPE_LENGTHS[ddicType]`（长度锚在类型表上）；
3. 断言上述 9 个工具的 `description` 输入都声明了同一上限，且被证伪的 `limited to 60 characters` 不会回来。

## 2. 根因

助手的接口构造器**所有助手共用一处**：`scripts/bootstrap-sap-helper.ps1` 中 `ls_import-parameter = 'IV_DESCRIPTION'`（L16738）紧跟 `ls_import-dbfield = 'TSTCT-TTEXT'`（L16739），位于按 `$FunctionName` 分叉的 `$operationDbField` 判断**之外**。因此该上限是**全局**的，而非按助手区分。

助手正文把该形参赋给 `DD01V` / `DD04V` / `DD02V` / `DD30V` / `DD25V` / `DD40V-DDTEXT` 与 `TNROT-TXT` —— 这些目标字段**都是 60 宽**。绑定上限的是**形参**而不是目标字段，故截断在助手正文执行前、于 RFC 边界静默发生，写入照常成功。这解释了为什么四处「60 characters」的声明长期未被发现：它们在目标字段一侧是正确的，只在形参一侧错误。

`src/table-allowlist.ts:29` 亦已记录更早的翻案：w200 上 `DD30V` 可读、其 `DDTEXT` 为 **C60**，且该表内存在 **145 条超过 35 字符**的描述 —— 即 37–60 字符的描述在本系统属正常，而形参只有 36。

**本次只声明、不强制**：拒绝超长 description 属于**收窄已接受取值**，按外部 RFC 设计纪律须显式批准，故留给用户裁定（见 §6）。

## 4. 证伪（证明新测试真的有牙齿）

按「证伪新回归测试」的做法，在 `dist` 内临时改坏常量后单跑该测试文件，再以 `npm run build` 还原：

| 证伪动作 | 预期 | 实测 |
| --- | --- | --- |
| `HELPER_DESCRIPTION_PARAMETER.ddicType` 改为 `TSTCT-TTEXTX` | 类型断言红 | ✖ `the generator's IV_DESCRIPTION type and HELPER_DESCRIPTION_PARAMETER must agree`（exit 1） |
| 仅把 `length` 由 36 改为 60（类型不动） | 长度断言红 | ✖ `TSTCT-TTEXT is CHAR 36`（exit 1） |

**第一版实现曾在此暴露缺陷**：初版只断言「契约文案含 `CHAR ${常量.length}`」，而文案正是由该常量插值生成，属**同义反复** —— 单独改 `length` 为 60 时测试**照样通过**（实测 exit 0）。据此补入 `DESCRIPTION_PARAMETER_TYPE_LENGTHS` 交叉校验后才具备牙齿。此教训与本仓既有注释（「期望值刻意不取自本地长度表」）同源。
