### 4.4 根因（读当前源码核定，非推测）

`src/write-prechange-evidence.ts` 的变更前观测按工具名分派：`cleanup_transport_entries`、`create_transport_request`、`add_objects_to_transport`、SmartForm/增强/屏幕/消息类/DDIC/`delete_sap_lock`、`release_transport_task`、`run_abap_program` 各有专支，**其余工具全部落入末尾的 `observeSourceTarget()`**。该函数的目标身份来自 `sourceObject(name, input)`，而 `sourceObject()` 只识别 `create_object_programmatically`、`delete_abap_source_object`、`create_test_include`、`manage_text_elements`，以及「`input.objectName` 存在」这一通用分支。

`release_background_job` / `cancel_background_job` 的入参是 `jobName` + `jobCount`，**没有 `objectName`**，因此：

1. `uri` 为空 ⇒ 不走 `inspectSource`；
2. `sourceObject()` 返回 `undefined` ⇒ `throw new Error("write target has no readable source identity")`；
3. 该错误被捕获并记为告警 `source: observation failed (<hash>)`，`evidence.exists` 保持 `null`；
4. 闸门按契约抛出「could not establish whether background job … exists」并**在接触 SAP 之前**终止。

这也解释了 `.doc/code-update-20260930-114216.md` 中同一工具的失败回执（内层哈希逐字相同）——**该失败是确定性的、与作业状态无关、与实例无关**，两次实测（11:42、14:47）与一次重启后的重放完全一致。

`src/mcp.ts:1533-1539` 已经为这两个工具补了 `targetKey`/`targetSummary`（所以回执能正确写出 `background job ZTEST0018 with job count 16413100`），但 `write-prechange-evidence.ts` 侧**没有对应的观测分支**。同一类缺口此前已按同样方式修过三次（`delete_sap_lock` 2026-09-28、`release_transport_task`、`cleanup_transport_entries`），注释都写明了「没有这一支，回执会读成 ADT target 空串，闸门会在接触 SAP 前拒绝写」。

## 7. 剩余风险与优先级

1. **高**：`jobs` 族两个写工具对**任何**输入都必然失败（`sourceObject()` 无对应分支 ⇒ 观测目标身份缺失 ⇒ 闸门失败关闭）。工具本身是**安全**的（SAP 零写入），但**功能上不可用**，`jobs` 族因此不可能闭环。修法明确且有三处先例：为 `release_background_job` / `cancel_background_job` 在 `src/write-prechange-evidence.ts` 增加一支，以 `TBTCO` 的 `JOBNAME`+`JOBCOUNT` 直读作为观测源，并补齐 `sourceObject()` 的对应身份。
2. **中**：`read_background_job_details` / `read_background_job_log` 对「已排定、从未运行」的作业返回无归因的 `READ_ONLY_UNSUPPORTED`（`make_time` 宏 `RETURN` 中止整个函数模块）。对已完成作业可用，对该状态不可用；该缺口使助手的作业读路径存在一个状态相关的盲区。
3. **低**：`runtime-resources` 的 `boundary` 新增了「助手行数上限 200 / `read_workload_directory` 只回采集器索引」两条长期限制的正式表述——它们是**能力边界**而非待建缺口，若日后要求完整回传须另立需求。
