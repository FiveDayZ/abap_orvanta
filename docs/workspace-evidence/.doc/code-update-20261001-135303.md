### 1.1 缺陷六：`modify_background_job` 把已排定作业改成已释放（仓库助手）

- 对象：`Z_ORVANTA_MCP_DYNPRO_API`（函数组 `ZORVANTA_MCP_CORE`），载体程序 `ZORVANTA_MCP_DYN227`
- 根因（读 SAP 标准源码定案）：`BP_JOB_MODIFY` 在 `dont_release='X'` 之下先置 `release_privilege_given = btc_no`（第 408 行），但 `dialog='N'` 的 opcode-16 分支走 `BP_JOB_EDITOR`（`job_editor_opcode = btc_check_only`，第 538 行），后者第 179 行调 `PERFORM check_release_privilege`（FORM 在 `LBTCHF12:707`，重查 `S_BTCH_JOB/JOBACTION='RELE'`），把该全局改回 `btc_yes`，于是第 647 行 `new_status = btc_released`，最终由 `update_modified_jobdata`（`LBTCHF13:356+`）把 `mod_jobhead-status` 落库。**`dont_release` 对该路径结构性无效**。
- 修法：两个分支（header / step）在 `BP_JOB_MODIFY` 落库、读回 `TBTCO` 之后，若读回状态为 `'S'` 而改动前为 `'P'`/`'Z'`，显式再调一次 `BP_JOB_MODIFY`，`opcode = 18`（`btc_derelease_job`）把作业改回 `btc_scheduled`；若 SAP 拒绝（`cant_derelease_job` 等）或以 `'S'` 收场，回 `JOB_DERELEASE_FAILED` 并附 SAP `subrc`，**不当作成功**。
- 同时把两个分支的状态闸门由 `<> 'P' AND <> 'S' AND <> 'Z'` 收紧为 `<> 'P' AND <> 'Z'`：已释放的作业一律拒绝（`JOB_NOT_MODIFIABLE`）。依据：从未运行的作业不可能持有 `'S'`，且 `reset_release_info_in_db`（`LBTCHFXX:2063`）只删 `TBTCS`/`BTCEVTJOB` 的开始条件行、不触碰 `TBTCO`，`SDLSTRTDT/SDLSTRTTM` 会留存，若允许改已释放作业就需要一次静默再释放。
- 部署：载体 `ZORVANTA_MCP_DYN227` 由人工在 SE38 按 F8 生成并激活；回执 `DONE: helper regenerated; 50 capability rows written`；`get_capability_report` 复核 `sourceHash = 74cc22feb991f5b3ec5e34957a58c1201e571a34611186de7e817de1d0d9ff0a`，与导出正文 sha256 逐位一致。

### 1.2 缺陷七：`make_time` 宏内的 `RETURN` 中止整个函数模块（运维助手）

- 对象：`Z_ORVANTA_OPS_READ`（函数组 `ZORVANTA_LOG`），runtime 全量变体
- 现象：`read_background_job_details` 对**任何尚未运行完的作业**只回裸 `READ_ONLY_UNSUPPORTED`（无 `reason`）；只有 `STATUS='F'`/`'A'` 的作业可读。
- 根因（25 行真值表取样定案，见 `.cache/r273-truth-table.json`）：`make_job` 宏对 `TBTCO-STRTDATE`/`ENDDATE` 为空（`STATUS` 为 P/S/Y/Z，即一切未跑完的作业）时仍调用 `make_time`；`make_time` 是 `DEFINE` 宏，**ABAP 宏体内的 `RETURN` 退出的是外层处理块（即整个函数模块）**，于是请求在构造作业头时中止，`ev_result` 停在分派前无条件写入的兜底值 `READ_ONLY_UNSUPPORTED`。判据：`ZWMS_8050`/`14141600`（`STATUS='S'`，`SDLSTRTDT=20261001` 合法）同样中止，排除「时间不可表示」这一解释；`ENDDATE` 是否为空与成败完全一致。
- 为何此前不可见：只有 `JOB_LOG` 走 `JOB_LOG_DIAGNOSTIC` 别名置诊断位，`JOB_DETAILS` 是裸动作，`job_stage` 在正常模式下是空操作，所以 `JOB_DETAILS` 连阶段名都拿不到。用 `read_background_job_log`（走别名）取得助手自报 `reason: "JOB_TIMESTAMP"`。
- 修法（按用户裁定 ①，只改生成器 `scripts/operational-log-source.mjs`）：
  - `make_time` **不再含任何 `RETURN`/`CHECK`/`EXIT`**，改为纯正向条件把有效性写入新变量 `lv_time_valid`；时间判空用 `CO '0123456789'` 而非 `IS INITIAL`（`TYPE T` 的午夜 `'000000'` 的 `IS INITIAL` 为真，是 DYN224 的老坑）。
  - `make_job` 三个调用点各自判 `lv_time_valid`：无效则渲染 `null`，不再中止。
  - 窗口校验（`lv_from`/`lv_to`）与 TemSe 消息记录两处**保留拒绝**，但改为在调用点显式 `RETURN`，阶段名仍可归因。
  - 系统日志循环改为跳过该单条记录（`CONTINUE`），不再因一条不可渲染记录丢弃整个结果。
  - 服务端同批适配：`src/operational-logs.ts` 的 `backgroundJobSchema.scheduledSystemTime` 由非空改为 `.nullable()`，`JOB_SEARCH` 的窗口比对把 `null` 作为具名不一致拒绝；`operationalLogReasons` 中 `JOB_TIMESTAMP` 的注释改为「现在只属于仍须拒绝的调用点」。
- 部署：`.cache/r274-deploy-ops-read-make-time.mjs --apply-approved` 走 `write_function_module_source`；接口指纹前后不变（`621a1362…`），正文 1797 → 1839 行；`.cache/verify-ops-read-body.mjs --variant=runtime` 回 `deployed_source_verified`，`sourceFingerprint = 527bbaa2d36f172ae656eaffbd24289a446a6f65634e9770c6a2c2912fe505c2`。
- 批准文件重钉：`%LOCALAPPDATA%\ABAP MCP Standalone\state\operational-log-approvals.json` 的 `sourceFingerprint` 由 `56176ac6…` → `527bbaa2…`，`interfaceFingerprint` 不变，`enabledSources`（`SM37`,`SM37_DETAILS`,`SP01`,`RUNTIME`,`SM21`）逐项保留。
- **第一次部署的教训**：首版去掉了 `job_stage` 但**保留了 `RETURN`**，于是中止点只是后移一层，真机回执变成 `JOB_PROT_AUTHORITY`。宏内必须彻底无早退，`RETURN` 本身才是缺陷。

## 5. 本批新暴露、**未修**的缺陷（超出本轮逐项授权，仅报告）

`read_background_job_log` 对**从未运行过的作业**（`TBTCO-JOBLOG` 为空）返回裸 `READ_ONLY_UNSUPPORTED`，助手自报阶段 `TEMSE_NAME`：

- 位置：`Z_ORVANTA_OPS_READ` 的 `JOB_LOG` 分支，`scripts/operational-log-source.mjs` 的 `IF ls_job-joblog(6) <> 'JOBLGX' … RETURN` 守卫。
- 性质：与 defects 六、七同族——**能力存在、但拒绝码不具名**。作业确实存在、工具确实支持该操作，只是尚无日志；回 `unsupported` 会让调用方误以为「本系统不支持读作业日志」。同类问题此前在 `USER_LIST` 分支已被修过（补 `USER_LIST_*` 阶段名）。
- 影响面：`read_background_job_log` 对一切未跑完的作业（`P`/`S`/`Y`/`Z`）。对已跑完作业（`F`/`A`）正常。
- 修法方向（未实施）：为空 `JOBLOG` 增加具名回执（如 `NOT_FOUND` 或空消息列表 `complete:true`），而非落到兜底码。
- 该助手正文的改动需用户逐项裁定；本记录不声称已修。
