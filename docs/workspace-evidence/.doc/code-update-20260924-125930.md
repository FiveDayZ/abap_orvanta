## 1. 本轮要解决的问题

`0.47.5` 已发布并部署，用户重启后按修复预期用 **CTS 任务号** `GR2K923428` 调用
`resume_ddic_table_activation`，结果**与修复前完全一致地失败**：

```
TRANSPORT_RECORD_FAILED: 请求类型不允许 [ TK / 886 ]
```

回执中的 `preChangeSummary` 为：

```json
{"target":"tabl object ZTPMC_TPRPI","requestedOperation":"resume_ddic_table_activation",
 "concurrencyGuard":"tool-specific SAP readback and lock checks",
 "transportNumber":"GR2K923428","automaticRollback":false}
```

即 `transportNumber` 仍是**原始任务号**，既无 `requestedTaskNumber`，也无 `transportResolution`，
`errorHash` 与最初事故 `e6d70fcc…` **逐位相同**。结论：`0.47.5` 的修复在真实服务中**根本没有生效**，
是一次 no-op 发布。

## 2. 根因（已证实）

`resolveWriteTransportNumber` 通过 `SapBackend.runQuery` 读 `E070`。该方法的**原生路径**
（ADT data preview，`runSapDataQuery`）在本 ECC 7.31 系统上必然失败：

```
SAP_DATA_QUERY_RESPONSE_INVALID: expected XML data preview; HTTP 200; mediaType=text/html;
root=unparsed; bytes=0. No empty result was inferred.
```

整个服务里只有 `execute_data_query` 能越过它——因为它自带 `rfc_read_table` 回退
（`src/tools.ts` 第 7195-7228 行，`parseSimpleTableSelect` + `this.readAbapTable(...)`）。
`0.47.5` 的解析器既没有这条回退，又把异常吞进 `catch { return null }`，
于是**每次调用都失败、失败被隐藏、任务号原样下发**，最终由 SAP 侧抛出 `TK/886`。

**实测证据**（`execute_data_query`，端口 4847）：

```json
"querySource": { "method": "rfc_read_table",
                 "nativeCode": "SAP_DATA_QUERY_RESPONSE_INVALID",
                 "representation": "sap_text_trimmed" }
```

`method` 落到回退分支、`nativeCode` 正是原生失败码，两者同时出现即证明原生路径不可用。

## 3. 修改内容

| 位置 | 变更 |
| --- | --- |
| `src/mcp.ts` `resolveWriteTransportNumber` | 读操作改为**注入**：新增第 3 参 `readRows(connectionId, container)`；返回值由 `string \| null` 改为 `WriteTransportResolution { requestedTaskNumber, unresolvedReason }` |
| `src/mcp.ts` `invokeWriteTool` | 新增第 6 参 `readTransportRows`；调用点由 `resolveWriteTransportNumber(values, backend)` 改为传入该读取器 |
| `src/mcp.ts` `createMcpServer` | 新增 `readTransportRows`：`assertTableAllowed("E070")` → `tools.readAbapTable({tableName:"E070", columns:["TRKORR","TRFUNCTION","STRKORR"], filters:[{column:"TRKORR",operator:"EQ",value:container}], maxRows:1})`；`status !== "ok"` 时**抛错**而非返回空行 |
| `src/mcp.ts` `writeOperationContext` | 第 4 参改为 `resolution`；摘要新增 `requestedTaskNumber` + `transportResolution`（发生替换时）与 `transportCheckWarning`（未能判定容器时） |
| `src/mcp.ts` 成功路径 note | 改用 `transport.requestedTaskNumber` |
| `src/version.ts`、`package.json`、`package-lock.json` | 版本 `0.47.5` → `0.47.6`（四处一致） |
| `test/write-transport-task-resolution.test.ts` | 重写为 9 个用例 |

**行为语义（保持"绝不静默"不变）**：

- 调用方给**任务号** → 解析为父请求后改写 `values.transportNumber`，回执同时写明
  `requestedTaskNumber`（调用方原值）与 `transportResolution`；成功结果追加一行说明。
- 调用方给**请求号** → 原样通过，摘要不增字段。
- **读取失败** → 不改写，摘要写 `transportCheckWarning: "E070 could not be read for <号> (<错误>); it was submitted unchanged"`。
- **`E070` 无该行** → 不改写，摘要写 `transportCheckWarning: "E070 has no row for <号>; it was submitted unchanged"`。
- 空 / 非字符串 → 完全不访问 SAP。

`E070` 仍在 D5-2 允许清单内（`table-query.ts` 第 117 行 `assertTableAllowed`，另在服务侧显式再断言一次）。
