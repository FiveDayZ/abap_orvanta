## 一、复测暴露的两处缺陷与根因

### 缺陷 1：正文锚点落在首个声明块，而非 FUNCTION 语句（助手 2.9/2.10）

- 现象：2.9 上线后复测，`SOURCE_MARKER_ERROR` 消失，但换成 `SOURCE_FINGERPRINT_CONFLICT: Function body changed since the reviewed read c3eb05cd…`。
- 取证方法：把助手报出的当前哈希与 SAP 侧两份文本（`READ_FUNCTION_INTERFACE` 载荷 36 行、ADT 视图 46 行）的所有连续区间 × 4 种行尾/裁剪组合做暴力比对，唯一命中 **载荷第 5..34 行**（`CLEAR:` 之后）——即助手把正文起点定在了 `DATA` 声明块的**末行之后**。
- 根因：SAP 侧 include 的 `FUNCTION x.` 是**自带句点、单行结束**的语句；而 2.9 那条判据在第 1 行只校验 `FUNCTION` 前缀、**不做句末 `.` 判断**，于是 `FUNCTION` 行永远不能成为锚点，扫描继续到"第一个以 `.` 结尾的行"= `DATA` 块最后一行 `lv_msg TYPE bapi_msg.`，正文从其后开始。服务端（`functionSourceSegments`）用的是"第一个以 `.` 结尾的行"，在载荷视图里恰好是 `FUNCTION x.` 自身，因此两侧起点差 4 行。
- 危害等级：**High（若守卫失效即为破坏性写入）**。该起点同时用于哈希与替换：守卫拦下的若是一次真实写入，助手会把 `DATA` 声明块整段删除。
- 本次**未造成任何破坏**：`SOURCE_FINGERPRINT_CONFLICT` 在任何 SAP 调用前中止（`get_version_history` 仍为 1 版、源码逐行未变）。

### 缺陷 2：末字符偏移越界（助手 2.10 首次实现）

- 现象：修完锚点后复测，助手侧 `HTTP 500 … Illegal access to a string (offset too large) (RABAX_STATE)`。
- 取证：`analyze_abap_dumps` 列出新增转储 `STRING_OFFSET_TOO_LARGE`（2026-09-25 14:17:50），内容直接指向助手 7264 行 = 新加的 `IF lv_fm_body_text+lv_fm_body_length(1) = '.'.`，偏移 34 越界。
- 根因：同文件 ELSE 分支取末字符前先 `lv_fm_body_length = lv_fm_body_length - 1.`，新分支漏了这一步；`lv_fm_body_length` 是右裁剪后的长度，末字符偏移应为 `length - 1`。
- 修正：新分支补同一句 `- 1`，与 ELSE 分支写法一致。

## 二、接口与行为变化

- 助手 `WRITE_FUNCTION_SOURCE` 的正文边界判据（第三处副本）改为：
  1. 有接口骨架（两处 `*"----`）→ 第 2 个分隔符之后；
  2. 无骨架时，第 1 个非空行必须是 `FUNCTION` 语句：
     - 该行**以 `.` 结尾**（单行语句）→ 正文从**下一行**开始；
     - 该行**未以 `.` 结尾**（接口跨行）→ 正文从其后第一个以 `.` 结尾的行之后开始；
  3. 两者都不满足 → 失败关闭（`SOURCE_MARKER_ERROR`，措辞未改）。
- 服务端 `functionSourceSegments` / 替身 `storedFunctionBodyRange` 判据不变（在载荷视图下两者与新判据等价），三副本语义自此一致。
- `minHelperProtocol`（`write_function_module_source`）：2.9 → 2.11；能力表行 `"WRITE_FUNCTION_SOURCE|2.11|W"`；21 处 `ev_version` 同步。
- 无接口、无参数、无返回结构变化；对既有调用方是纯缺陷修复。
