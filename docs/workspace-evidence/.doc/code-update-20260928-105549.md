### 3.1 用例 A：真实行与边界声明

首行实测（字段名即回执字段）：

```
alertSystem=GR2  monitorSet=SAP_CCMS_GRAPP2_GR2_00  alertDate=20250603  alertTime=224816
cleared=true  open=false  client=[200]  severity=[50]  objectName=Background
```

`notes` 共 7 条，四条关键边界声明全部在位：

| 必需声明 | 断言 | 实测 |
| --- | --- | --- |
| 不是 RZ20 实时监视、空结果不等于健康 | 含 `not the RZ20 live` | ✅ True |
| 行序未指定、非最新若干条 | 含 `Row order is unspecified` | ✅ True |
| 表非按客户端隔离 | 含 `not client-isolated` | ✅ True |
| 结果不是总数 | 含 `never a total` | ✅ True |

**关于 `status:"partial"` / `truncated:true` 的更正**：本用例 `maxRows=5` 而 `ALALERTDB` 持有远超 5 行，因此**截断是正确行为**，`partial` 是诚实状态而非缺陷。此前口头预期写的"`status: ok`、5 行、`truncated:false`"是**错的**（把 0 行用例的期望照搬到有数据用例上）；正确期望是 `partial` + `truncated:true`。0 行用例（B）才是 `ok` + `truncated:false`。

### 3.2 用例 B：0 行不等于健康

`openOnly:true` 即 `GONEDATE EQ ''`，返回 0 行且 `truncated:false`。这与同日只读取证中 `COUNT(*) WHERE GONEDATE='' = 0` 完全一致，也是回执 notes 明确否认"系统健康"的原因（RZ20 读的是内存 MTE 树，本表不含）。

### 3.3 用例 C：九条件被预先拒绝

入参：`alertDateFrom`、`alertDateTo`、`clearedFrom`、`clearedTo`、`alertSystem`、`monitorSet`、`objectName`、`fieldName`、`client`（共 9 个条件，上限 8）。

拒绝原文：`Error: CCMS_ALERTS_SCOPE_INVALID: 9 conditions requested, the reader accepts 8`。

该判定位于 `collectCcmsAlerts` 内、`read(...)` 调用**之前**（`src/ccms-alerts.ts`：先做日期/互斥/条件数校验，再构造 reader 调用），故拒绝时不触 SAP。**说明**：运行时不具备"证明未触 SAP"的观测通道，此处依据的是校验语句在调用之前的源码顺序与单元测试中 `calls.length === 0` 的断言；不在本记录中把它表述为运行时观测。

## 8. 剩余风险与优先级

1. **`archive-alerts` 族仍未闭环（`partial`）**：`read_ccms_alerts` 已验证，但 `read_archive_status` 仍 `unverified`（需先部署 MAINT 的 `ARCHIVE_STATUS` 分支），且族缺口——归档文件明细——仍在（`ADMI_FILES` 在客户端 200 为空，无样本可描述）。**本记录不改变族闭环状态。**
2. **用例 A 的首行值不是基线**：表无排序，首行随数据变化；它只证明真实行能按文档字段解码，不得当作固定期望写进任何断言。
3. **截断语义易误读**：`maxRows` 上限触发时 `status` 为 `partial`、`truncated` 为 `true`，这不是失败。任何把 `partial` 读成异常的消费方需修正。
4. **"拒绝时不触 SAP"仅有源码顺序 + 单测支撑**，运行时无该观测通道。
