## 1. 结论

**`read_user_sessions` 的阻塞根因是 `USER_LIST` 分支的终止 `CATCH cx_root` 处理器静默吞掉了内核抛出的类异常。**

该处理器写出的回执，与「分支里每一个守卫 `RETURN`」写出的回执**逐字相同**（`status:unsupported` / `code:READ_ONLY_UNSUPPORTED` / 无 `reason` / 无 `calleeSubrc` / 无 `calleeException`），因此**类异常与「能力被拒」在回执层完全不可区分**。这解释了该工具自记录以来一直是「无归因失败」的全部现象。

## 2. 定位方法（可复用的判据）

### 2.1 先证伪两处旧前提

| 旧记录的说法 | 实测结论 |
| --- | --- |
| 「`fail_reply` 整体覆盖结果、丢弃 `lv_tail`」 | **不成立**。展开体是 `CONCATENATE lv_base … '",' lv_tail INTO ev_result.`，`lv_tail` 是被拼接进去的；服务端 `helperAnswer` 也**早已**会转写 `calleeSubrc`/`calleeException` |
| 「终止 `CATCH cx_root` 吞掉运行时异常」 | **表述错误但结论方向对**。它**不能**吞掉运行时错误（那会产生转储并终止程序），**但能**吞掉**基于类的异常**——这正是本例 |

### 2.2 判据：同一路径、仅入参不同而结果不同 ⇒ 差异必在调用内部

| 入参 | 回执 | 推理 |
| --- | --- | --- |
| `maxRows: 500` | `reason=USER_LIST_LIMIT` | 500 > 200，在 `TRY` **之前**的限值守卫就 `RETURN`，阶段回执**未被覆盖** |
| `maxRows: 200` | **无 `reason`** | 200 通过限值守卫、**进入 `TRY`**，阶段回执被 `CATCH` 覆盖 |

两者走的是**同一条工具路径、同一份正文**，唯一变量是行上限 ⇒ **差异只能由 `TRY` 内部解释** ⇒ 定位到 `CATCH`。

**这个判据的关键价值**：`RUNTIME_RESOURCES_MAX_ROWS = 500` 而 `HELPER_ROW_CAP = 200`，**服务端放行 500、助手限值守卫拒绝 500**，于是存在一个「必然触发助手守卫」的合法入参。此前用 50/200 试过多次都得到逐字同形的结果，正是因为两者**都不触发任何守卫**。

### 2.3 已排除的假设（勿重复）

- **不是**服务端吞字段：`src/operational-logs.ts:526-530` 明确允许 `unsupported` + `READ_ONLY_UNSUPPORTED` 携带 `reason`；`src/mcp.ts:60` 也转出 `reason`。
- **不是** `runtimeHelperOutcome` 丢字段：无 `reply` 时只丢 `calleeSubrc`/`calleeException`，`reason` 是转出的。
- **不是**别名未生效：`maxRows=500` 拿到 `reason=USER_LIST_LIMIT` 已证明别名与六个阶段名全部在线可用。
- **不是** `readDefinition` / 审批 / 指纹：`failure()` 把未识别错误映射成 `RUNTIME_RESOURCES_CALL_FAILED`，而观测值是 `READ_ONLY_UNSUPPORTED`，只能来自助手回执本身。
- **不是**转储：`analyze_abap_dumps` 在 2026-09-30 零条目。

## 3. 修复内容（一处）

`scripts/runtime-read-source.mjs` 的 `USER_LIST` 分支终止处理器，由：

```abap
  CATCH cx_root.
    lv_tail = '"kernelRowCount":"0","rows":[],"truncated":false}'.
    fail_reply 'unsupported' 'READ_ONLY_UNSUPPORTED'.
  ENDTRY.
```

改为：

```abap
  CATCH cx_root INTO lv_exref.
    lv_tail = '"kernelRowCount":"0","rows":[],"truncated":false}'.
    CLEAR lv_class.
    TRY.
        lv_class = cl_abap_classdescr=>get_class_name(
          p_object = lv_exref ).
      CATCH cx_root.
        CLEAR lv_class.
    ENDTRY.
    IF strlen( lv_class ) > 60. lv_class = lv_class(60). ENDIF.
    CLEAR lv_json.
    json_field ',"calleeException":"' lv_class.
    CONCATENATE lv_json '}' INTO lv_json.
    CONCATENATE '"kernelRowCount":"0","rows":[],"truncated":false'
      lv_json INTO lv_tail.
    job_stage 'USER_LIST_EXCEPTION'.
    CONCATENATE lv_base
      '"status":"unsupported","code":"READ_ONLY_UNSUPPORTED",'
      '"reason":"USER_LIST_EXCEPTION",' lv_tail INTO ev_result.
  ENDTRY.
```

设计要点：

1. **命名阶段**：`USER_LIST_EXCEPTION` 与既有的 `SYSTEM_READ_EXCEPTION` 同族。
2. **无条件写入**：`job_stage` 单独调用在正常模式下是**空操作**，只调它仍会留下裸回执。这里照 `SYSTEM_READ` 先例，在 `job_stage` 之后再无条件构造 `ev_result`。
3. **携带异常类名**：`calleeException` 是回执里既有的字段（上限 64 字符，故截断到 60）。取类名的调用包在**嵌套 `TRY`** 里——`CATCH` 内的方法调用本身可抛，该处理器不得把可诊断的失败变成空回执。
4. **不引入类型并集改动**：`lv_exref TYPE REF TO cx_root` 与 `lv_class TYPE string` 加在片段的 `runtimeReadDeclarations`，服务端**零改动**（除闭集枚举加一个名字）。

同批把 `USER_LIST_EXCEPTION` 加入 `src/operational-logs.ts` 的 `operationalLogReasons` 闭集。
