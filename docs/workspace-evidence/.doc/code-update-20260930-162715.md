## 2. 语义规则的权威来源（不是凭记忆写的）

规则取自 SAP 官方关键字文档 **`arith_exp - Calculation Type and Calculation Rules`**（SAP NetWeaver AS ABAP 7.51）：

`https://help.sap.com/doc/abapdocu_751_index_htm/7.51/en-US/abenarith_type.htm`

（入口：`abencalculation_type_glosry.htm` → `abenarith_type.htm`。）文档给出的原文规则，本层逐条实现：

| 文档规则（原文要点） | 本层实现 |
| -------------------- | -------- |
| 计算类型按优先级取全部操作数中最宽者：decfloat16/34 → decfloat34；f 或使用 `**` → f；p → p；int8 → int8；i、b、s → i | `calculationTypeOf()` + 优先级 `rank`，取最大 |
| 非数值类型算作：**d、t 按 i**；**c、n、string 按 p**；**x、xstring 按 i** | 同一映射表 |
| 计算类型 i/int8：整数运算，"每个非整数的子项（除法之后）按商业方式舍入到最近的整数"；溢出抛 `CX_SY_ARITHMETIC_OVERFLOW` | `roundHalfAwayFromZero()`（半值远离零）+ `withinRange()` |
| 计算类型 p：定点十进制，"**内部精度 31 位**"，整数部分溢出后重试 63 位；"多余小数位不抛异常，而是**对每个子项按商业方式舍入**" | 精确十进制运算（BigInt 缩放），**31 位处拒绝**（见 §3） |
| 计算类型 f：平台二进制浮点，"子项**可能产生舍入误差**" | **按名拒绝** `TABLE_QUERY_EXPRESSION_FLOAT` |

## 3. 三个"文档没规定、由本层决定并写明"的点

1. **没有目标字段，小数位从调用方写下的位数来。** ABAP 把表达式结果转换到被赋值的字段类型上，计算类型 p 的小数位正是由那个字段决定；`SELECT` 列表没有这样的字段。本层的规则：`+`/`-` 取两个操作数中较宽的小数位，`*` 取两者之和，**永不丢弃小数位**（ABAP 自己的算术也存不下超过 63 位）。
2. **`/` 在其小数位不确定时拒绝、在文档确定时精确执行。** 计算类型 i/int8 下文档是确定的（商业舍入到整数，已实现）；计算类型 p 下小数位取决于缺失的目标字段，故 **`/` 按名拒绝** `TABLE_QUERY_EXPRESSION_DIVISION_SCALE`，而不是自己编一个尺度。
3. **超过 31 位就拒绝，而不是保留 ABAP 会舍掉的位数。** 文档说 p 的精度是 31 位、多余小数位被商业舍入，因此一个宽于 31 位的子项是 ABAP **会舍入**的；公布未舍入的位数就等于公布了 SAP 永远不会产生的数。SQL 方言在这里会给出精确的 `DECIMAL(26,4)`（精确乘积），本层**不跟 SQL、跟 SAP**。代码注释把这一处分歧写明了。

## 4. 类型来源：DD03L，而不是一张手写的类型名表

真机只读取证（`SELECT TABNAME, FIELDNAME, INTTYPE, DATATYPE, LENG, DECIMALS FROM DD03L WHERE ...`，273 行、**未截断**）：

| 事实 | 证据（w200 实测） |
| ---- | ----------------- |
| `DD03L` 在白名单内且带完整类型事实 | 每字段 `INTTYPE/DATATYPE/LENG/DECIMALS` 齐备 |
| **`INTTYPE` 不足以分类** | `INT4` 字段的 `INTTYPE` 是 **`X`**（`X\|INT4\|000010\|000000`），与字节字段同为 `X`；必须用 `DATATYPE` |
| Include 伪分量在 DDIC 里是空类型行 | 出现 `\|\|000000\|000000` 行（读路径本来就排除 `.` 开头的名字） |
| 读取器文本**保留声明小数位** | `T006.ADDKO` 是 `DEC(9,6)`，真机返回 **`"0.000000"`**（6 位小数逐字保留） |
| FLTP 走**科学计数法** | `T006.TEMP_VALUE`/`PRESS_VAL` 真机返回 **`"0.000000000E+00"`** |
| NUMC 文本带前导零 | DD03L 的 `LENG`/`DECIMALS` 返回 `"000010"`/`"000006"` |

结论：操作数的**小数位是自描述的**（P 字段的文本就是声明小数位），而**类型**必须从 DDIC 读 `DATATYPE`。这也解释了为什么现有 `SUM` 会在 FLTP 上按"非十进制"拒绝——那是同一事实的表象。

## 7. 证伪（每条核心判断都要能被推翻）

`.cache/r26-falsify.mjs` 把三处判断分别退回 `dist/src/table-expression.js`，每次只改一处、跑完立即复原：

| 退回的判断 | 还原成的错误行为 | 结果 |
| ---------- | ---------------- | ---- |
| 商业舍入（半值远离零） | 直接截断 | FALSIFIED（exit 1） |
| 乘积的小数位 = 两者之和 | 退回"取较宽者" | FALSIFIED（exit 1） |
| 浮点操作数按名拒绝 | 不再拒绝（改写为"值非十进制"，指向错误的原因） | FALSIFIED（exit 1） |
| 复原后重跑该测试文件 | — | exit 0 |

**测试当场抓到的一处真实缺陷（已修）**：初版在**收集计算类型的同时就解析了操作数值**，于是 FLTP 字段以"值不是十进制数"被拒绝——而科学计数法只是同一事实的表象，真正的原因（二进制浮点计算，文档自己说子项可能带舍入误差）才是应当告诉调用方的那一个。已改为**先定计算类型、再解析值**，并由此让 `TABLE_QUERY_EXPRESSION_FLOAT` 成为该类输入的拒绝码。

## 9. 剩余风险

1. **没有独立预言机。** 表达式结果的正确性依据是官方文档规则 + "算不准就拒绝"，无法与 SAP 的同表达式结果做差分比对（原因见 §8）。分工上是清楚的：**凡不能保证精确的，本层拒绝**，因此"更保守"是它的默认偏差方向。
2. **第 31 位处拒绝比 ABAP 更严**：ABAP 会把 31 位以外的小数位商业舍入后给出结果，本层直接拒绝。这会拒掉一些 ABAP 算得出来的表达式（例如两个 `DEC(15,2)` 相乘），是有意的取舍，已在代码与文档中写明，并把 SQL 的对照做法一并说明。
3. **`DATATYPE` 的取值集合来自真机抽样**（8 张表的 273 个字段），未覆盖 `ACCP`/`LCHR`/`DF16_*` 等冷门类型；`calculationTypeOf()` 对无法归类的类型返回 `undefined`，由调用方按名拒绝，而不是猜一个计算规则。
4. **`d`/`t` 按 `i` 参与运算**会得到"日期数字加一"（`20260930 + 1 = 20260931`）这种结果——这是文档规定的语义（d as i），不是日期运算；已在用例中钉住，避免被误当成日期算术。
