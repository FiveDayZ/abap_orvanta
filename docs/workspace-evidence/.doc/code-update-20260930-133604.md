## 2. 归因前提的两处更正（本轮最重要的发现）

本轮开始前，`read_user_sessions` 的阻塞被记录为「`fail_reply` 整体覆盖结果、丢弃 `lv_tail`」。**读源码后该结论不成立**，必须更正：

### 2.1 `fail_reply` 并不丢弃 `lv_tail`

`fail_reply` 的展开体是：

```abap
CONCATENATE lv_base '"status":"' &1 '","code":"' &2 '",' lv_tail INTO ev_result.
```

诊断字段是**被拼接进去**的。服务端也**确实**会转写它们：`src/runtime-resources.ts` 的 `helperAnswer` 在 `calleeSubrc` / `calleeException` 存在时把它们推进告警行（该函数与 `RuntimeHelperReply.reason` 字段都早已存在）。

而实测告警是 `USER_LIST: READ_ONLY_UNSUPPORTED`，**既无 `calleeSubrc` 也无 `calleeException`** ⇒ 中止点**不在**写这两个字段的那两条路径（`sy-subrc = 1` 与 `sy-subrc <> 0`）上。

### 2.2 `CATCH cx_root` 不可能吞掉运行时错误

上一条推论曾指向 `USER_LIST` 分支的终止 `CATCH cx_root`。**该推论错误**：真正的 ABAP 运行时错误会产生**短转储并终止程序**，`CATCH cx_root` 只能捕获**基于类的异常**，对转储无效。

实测支持这一点：`analyze_abap_dumps` 的清单只有 **9 条、全部 `OBJECTS_NOT_CHAR`、时间戳 2026-09-29 15:59:24–32**，**2026-09-30 没有任何转储** ⇒ round-19 与今天的 `read_user_sessions` 调用**都没有转储**，返回的是正常回执。

## 3. 改动内容（一处，全部落在 `USER_LIST` 分支）

### 3.1 该分支此前完全没有归因

生成正文 `:713-714`（改前）：

```abap
  lv_tail = '"kernelRowCount":"0","rows":[],"truncated":false}'.
  fail_reply 'unsupported' 'READ_ONLY_UNSUPPORTED'.
```

它**在最前面无条件写一份默认回执**，之后每个守卫只 `RETURN.`。于是**范围拒绝、上限拒绝、授权失败、被调方子返回码**四种完全不同的原因**全部报成裸 `READ_ONLY_UNSUPPORTED`**，与「守卫返回」彼此无法区分 —— 与 round 18 之前的 JOB 分支同族。

### 3.2 加入六个阶段名

每个写在它所跟随的判据**之后**，故回执里的 reason 是**最后通过**的那一项、中止语句是它的下一条：

| 阶段名 | 位置 |
| --- | --- |
| `USER_LIST_SCOPE` | 参数范围守卫（14 个参数须为 INITIAL）之后 |
| `USER_LIST_LIMIT` | `iv_limit` 上限守卫之后 |
| `USER_LIST_CALLEE` | 进入 `TRY`、调用 `TH_USER_LIST` 之前 |
| `USER_LIST_AUTHORITY` | `sy-subrc = 1` 分支，写 `calleeException` 之后 |
| `USER_LIST_SUBRC` | `sy-subrc <> 0` 分支，写 `calleeException` 之后 |
| `USER_LIST_ROWS` | `DESCRIBE TABLE` 之后、渲染循环之前 |

### 3.3 只在传输层存在的诊断别名

`job_stage` 只在 `lv_body_check='X'` 或 `lv_diagnostic='X'` 时写 `ev_result`（正常模式下是空操作）。因此同批增加别名：

- 服务端 `src/operational-logs.ts` 的 `execute` 构造入参处，`IV_ACTION` 由 `USER_LIST` 替换为 `USER_LIST_DIAGNOSTIC`（与既有的 `JOB_LOG` → `JOB_LOG_DIAGNOSTIC` 同一模式）。
- 助手前导把 `USER_LIST_DIAGNOSTIC` 映射回 `USER_LIST` 并置 `lv_diagnostic = 'X'`。

**为何安全**：别名**永不出现在回执里**（助手在派发前就把它换回真名）；成功时该分支自己的收尾 `fail_reply 'ok' 'OK'` 会**覆盖**阶段回执，故成功路径零影响。

**为何不改类型并集**：初版把 `USER_LIST_DIAGNOSTIC` 加进 `RuntimeHelperRead` / `RuntimeReadAction` 的类型并集，导致 `mcp.ts` 与 `execute` 两处赋值链逐层报 `TS2345`。改为在 `execute` 一处做别名后，**没有任何类型被放宽**，改动面反而更小。

### 3.4 测试扫描清单的补正

`test/operational-logs.test.ts` 的 `GENERATOR_FILES` 原为两个文件，**漏了 `scripts/runtime-read-source.mjs`**。该片段同样发出阶段名，漏扫会让服务端闭集接受一批「看起来无人产生」的 reason —— 正是该用例要拦的漂移。已补入。
