## 1. 缺陷（R-20，High）

助手把要执行的操作放在 `IV_OPERATION` 里，而该参数是**定长 DDIC 字段**。超过其长度的操作码会在 RFC 层被**静默截断**，因此永远匹配不到助手的 `WHEN` 分支，落到 `WHEN OTHERS` 并返回"不支持该操作"——**即使助手的自述能力清单里列着这个操作**。

| 工具 | 助手 | 操作码 | 长度 | 上限 |
| --- | --- | --- | --- | --- |
| `resume_ddic_table_activation` | `Z_ORVANTA_MCP_DDIC_API` | `RESUME_TRANSPARENT_TABLE_ACTIVATION` | 35 | **32** |
| `manage_classic_badi_implementation` | `Z_ORVANTA_MCP_EXECUTE` / `_DYNPRO_API` | `MANAGE_CLASSIC_BADI_IMPLEMENTATION` | 34 | **30** |
| `delete_enhancement_implementation` | 同上 | `DELETE_ENHANCEMENT_IMPLEMENTATION` | 33 | **30** |
| `read_enhancement_implementation` | 同上 | `READ_ENHANCEMENT_IMPLEMENTATION` | 31 | **30** |

参数长度来源（线上实测）：DDIC 助手 `IV_OPERATION` 声明为 `BAPIRET2-PARAMETER`（`DD03L.LENG = 000032`）；`Z_ORVANTA_MCP_EXECUTE` 与 `Z_ORVANTA_MCP_DYNPRO_API` 声明为 `RS38L-NAME`（`000030`）。

### 根因之外的两个放大器

1. **文档口径错误**：此前文档写"操作码 ≤42 字符（72 列守卫）"，只覆盖了**生成期行宽**约束，**遗漏了运行期参数长度**约束。后者更隐蔽——本地测试与编译都不会发现。
2. **能力判定结构性不可见**：可用性由助手**自述的静态清单**推导，而增强/BAdI 族的能力组**根本没有固定任何操作码要求**（`src/tool-registry.ts` 中该族工具行的元组在最低助手版本 `"2.6"` 处结束、无操作码元素），于是判定"只看协议版本"。实测能力报告原文即自证：*"the registry pins no operation requirement for these tools, so this verdict rests on the protocol version alone"*。因此 4 个工具全部报 `available`，属**假阳性**。

## 8. 事后更正（2026-09-22 11:46，父代理自查）

本记录 §4 的交叉核对结论"无'已声明但不可派发'者"**数据无误**，但该措辞隐含的**根因框架是错的**，在此更正，以免误导后续读者：

- 本缺陷**不是**"能力表声明了某操作、而派发分支缺失"的不一致。**能力表行与 `WHEN` 字面量始终互相一致**——二者是**一致地、共同地不可达**：35 字符的操作码在到达 `CASE` **之前**就被 RFC 层截断为 32，因此 `WHEN` 永不匹配。
- 该一致性**早已被双向守卫**：`test/helper-capabilities-payload.test.ts:401-415`（DDIC）与 `:94-107`（repository）解析**生成后**的 CASE `WHEN` 子句并与能力表做**集合相等**断言；`:417-436` 另断言 DDIC 表与 `SapDdicOperation` 联合完全一致。
- **真正缺失的守卫**是"操作码字面量长度 vs 所属助手 `IV_OPERATION` 参数长度"的关联检查——这才是本记录 §3.2 新增守卫所闭合的缺口。
- ⇒ **不存在"第二道对应关系守卫"待建**；此前向 D6-3 写入方下达的该交付项**已撤回**。
- 教训：把"**一致但不可达**"误判为"**声明与实现不一致**"，会去建一道**已经存在**的守卫。**判断缺口之前必须先把已有守卫读一遍。**
