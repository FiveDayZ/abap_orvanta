## 1. 批准与范围

用户在当前任务中选定"下一步实施哪一条路线"为 **`query` 闭环**。该族缺口句原本列出五项缺失：
右联接、全联接、交叉联接、表达式、子查询、`LIMIT`。

**本批只做能被精确表达的那一半，并显式声明另一半未做**：

| 缺口项         | 本批处置                                                                       |
| -------------- | ------------------------------------------------------------------------------ |
| 右联接 `RIGHT` | **实现**（保留本次引入的表，未匹配的左侧写读取器空串）                         |
| 全联接 `FULL`  | **实现**（两侧都保留）                                                         |
| 交叉联接 `CROSS` | **实现**（无 `ON`，笛卡尔积；写 `ON` 按名拒绝）                              |
| `LIMIT`        | **实现**（必须最后子句，排序**之后**切片，不能豁免完整性判据）                 |
| 表达式         | **未做**（见 §8：需要服务端复刻 SAP 的 NUMC/DATS/PACKED 语义，属未裁定需求）    |
| 子查询         | **未做**（同上）                                                               |

**因此本批不宣告 `query` 族闭环**：缺口仍非空，族状态继续是 `partial`，必需族闭环数仍是 **10/14**。
不得为凑闭环清空缺口——这一点在 §8 作为待裁定事项交回用户。

## 3. 语义决定（每条都进了拒绝文案与文档）

1. **`RIGHT JOIN` 保留本次引入的表**，`FULL JOIN` 两侧都保留；未匹配的一侧按读取器口径写空串
   （与既有的"LEFT 的可选侧留空"同一表示）。
2. **`CROSS JOIN` 不接受 `ON`**：写了 `ON` 是"配对全部"与"只配对匹配项"自相矛盾，按名拒绝
   （`TABLE_QUERY_JOIN_CROSS_ON`），不改写含义。
3. **`WHERE` 不得触碰外联接未保留的那一侧**：规则由"`LEFT` 的可选侧"推广为"按哪一侧被保留"——
   `LEFT` 本次引入的表、`RIGHT` 它之前的表、`FULL` 两侧都算；拒绝码不变
   （`TABLE_QUERY_JOIN_WHERE_OUTER_COLUMN`）。理由是每条谓词都下推到它所指表的**那一次读取**，
   在下推层删除行等价于删除这些行本会产生的联接行，在保留侧正确、在未保留侧错误。
4. **外联接仍必须是最后一个联接**（`TABLE_QUERY_JOIN_OUTER_NOT_LAST`），规则从 `LEFT` 扩展到
   `LEFT`/`RIGHT`/`FULL`。
5. **`LIMIT` 必须是最后一个子句、只收一个整数**（其余形式按名拒绝 `TABLE_QUERY_LIMIT_FORM`）；
   被静默忽略的 `LIMIT` 会用另一个行数回答另一个问题。
6. **`LIMIT` 约束答案、不约束读取**：读取次数与行上界都不变；切片发生在 `ORDER BY` **之后**。
7. **`LIMIT` 不能把不完整的读取变成完整的**：聚合与 `ORDER BY` 的完整性判据仍在切片之前、
   针对整个匹配集判定，截断即拒绝。`querySource.limit` 回报实际生效的上界，无该子句为 `null`。

## 4. 一处实现缺陷（由本批新测试当场抓住，已修正）

初版 `readGroupedRows` 把 `LIMIT` 放在了 `ORDER BY` **之前**切片：

```ts
// 错误（初版）
const limited = select.limit === undefined ? result : result.slice(0, select.limit)
return { rows: sortRowsByColumns(limited, select.orderBy), ... }
```

于是 `SELECT MANDT, JOBNUM FROM TBTCO ... ORDER BY JOBNUM DESC LIMIT 2` 返回的是"**先读到的两行
再排序**"（实测 `["0011","0009"]`），而不是"排序后的前两行"（应为 `["0011","0010"]`）。这正是
`LIMIT` 唯一容易写错的地方。新用例的断言直接抓到该差异，已改为先排序再切片。**该缺陷从未进入任何
真机路径**（在此期间 4849 一直运行本批之前的构建）。

## 8. 覆盖口径与待用户裁定的事项

`query` 族的缺口现只剩 **表达式** 与 **子查询** 两项。这两项不是"还没做"，而是**方式尚未裁定**：

- **方案 A（实现）**：在服务端实现一个能精确复刻 SAP 类型语义的表达式层与子查询执行层。风险是
  本方言的全部价值建立在"比较与取值都由 SAP 自己决定"之上，服务端自算会引入与 SAP 不同的
  NUMC/DATS/PACKED 语义——即"静默回答另一个问题"，正是本路径存在要避免的事。
- **方案 B（认定为平台边界）**：原生数据预览端点在本版本不可用，`RFC_READ_TABLE` 无法承担 plan，
  服务端自算会与 SAP 语义分叉 ⇒ 把"任意被 SAP 规划过的语句"写进 `boundary` 而不再是缺口。

**本批不自行选择**：把缺口清空即等于宣告闭环，而用户既有硬约束明确"`query` 族的真实缺失不得靠清空
gap 凑闭环"。故本批保持缺口非空、族状态 `partial`、必需族闭环 **10/14**，把 A/B 交回用户裁定。

## 9. 剩余风险

1. 新联接语义**尚无真机证据**（见 §7）；单元测试覆盖的是服务端拼装逻辑，不是 SAP 侧读取行为。
2. `CROSS JOIN` 的笛卡尔积只在服务端有界（`joinTableLimit=3` + 行上界 + `LIMIT`），SAP 侧每次仍是
   一张表的有界读取，因此不会产生超大 SAP 结果；但**跨 3 表的交叉联接会迅速触到行上界**，此时答案
   是"一页"而非完整匹配集，`truncated=true`。
3. `RIGHT`/`FULL` 的未匹配补齐在联接**触到行上界而提前停止**时被刻意跳过（未探测过的键看起来就像
   没有伙伴）。该保护在输出行上不可见，只在 `querySource.join.joinedRows` 上可观测，已有专门用例钉住。
4. `LIMIT` 与 `sortColumns`/`rowRange` 的关系不变：`LIMIT` 只作用于语句自身的答案，工具层
   `rowRange` 仍是对返回页的再切分。
