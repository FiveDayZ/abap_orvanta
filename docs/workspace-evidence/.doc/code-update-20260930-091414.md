## 1. 立项缘由

2026-09-30 步骤②完成（`.doc/code-update-20260930-090003.md`）后，`updates` 族的读侧已闭环，但族缺口仍在：

> `Failed updates can be read but never reprocessed.`

族内计划工具 `reprocess_failed_update` 不存在，且属写操作。用户本轮**授权单独立项**，范围限定为可行性判定与设计结论。

## 2. 结论

**在受支持的 SAP 接口范围内，`reprocess_failed_update` 无法实现。** 因此 `updates` 族剩余的缺口不是「一个还没建的工具」，而是「平台不向无 GUI 调用方暴露的能力」。按项目既有分列原则（族 `gap` 只放闭环前仍缺的**能力**，平台或目标固定的限制写 `boundary`），该族可改以只读口径闭环——**但这是需要用户裁定的结论，本轮未改动族定义**。

## 4. 三条被否决的路线

| 路线 | 做法 | 否决理由 |
| --- | --- | --- |
| A | 调用 `RSM13000` 的 FORM | 模块池 + 屏幕状态 + `MESSAGE A210`；且须改标准对象。项目明令禁止把模块池 FORM 原样搬进 RFC |
| B | 走 `UPD_CALL_SM13` | 末句 `CALL TRANSACTION 'SM13'`，对话框事务，RFC 无 dynpro |
| C | 助手自行复刻状态迁移（写 `VBHDR`/`VBMOD`/`VBLOG` + 启动分发器） | 要么依赖内核 `ThVBCall`（不可用），要么直接改更新系统内部状态——未发布接口且可能破坏更新队列；即便单独授权也不是受支持实现 |
