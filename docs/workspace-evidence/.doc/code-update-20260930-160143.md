其中一条为验证 `RIGHT JOIN` 的保留语义而写成"在 `ON` 里给两侧各加一个字面量条件"，真机返回：

```
TABLE_QUERY_JOIN_ON_ALIAS: ON A.TRKORR = 'ZZZ_NO_SUCH_REQUEST_OR_TASK' must name the table this

```

该拒绝本身是合法拒绝，但它逼出了原规则的来源追问：**"`ON` 里的字面量条件必须落在本次联接引入的表"这条规则，
只在 `LEFT` 上是安全的。** 见 §2。

## 2. 缺陷根因（静默回答另一个问题）

`ON` 中的"列 = 字面量"是一条"配对必须满足"的条件。方言把它下推到**该列所属表的那一次读取**。
下推会删除该表的行，因此只有**这次联接丢得起行的那一侧**才可以接受它：

| 联接类型 | 保留（丢不起）的一侧 | 可下推的一侧 | 旧规则 | 旧规则后果 |
| -------- | -------------------- | ------------ | ------ | ---------- |
| `INNER`  | 无（两侧都丢得起）   | 两侧皆可     | 本次引入的表 | 偏严，但用 `WHERE` 可等价表达，安全 |
| `LEFT`   | 本次引入的表为可选侧 → 保留的是**之前**的表 | **本次引入的表** | 本次引入的表 | **正确** |
| `RIGHT`  | **本次引入的表**     | **之前的表** | 本次引入的表 | **错误**：把谓词加到被保留侧的读取，删掉联接本该保留的行，且不报错 |
| `FULL`   | 两侧都是           | 无           | 本次引入的表 | **错误**：同上，且 `WHERE` 也无法表达 |

`RIGHT` 的错法是**静默的**：`A RIGHT JOIN B ON A.k = B.k AND B.k = 'X'` 会先按 `B.k='X'` 过滤 B 的读取，
于是结果里只剩 `B.k='X'` 的那一行，其余 B 行全部消失——而 SQL 语义要求这些 B 行以"A 侧为空"的形式保留。
这属于本项目明令禁止的"静默回答另一个问题"，比上一批那处切片顺序缺陷更严重（那处会被测试抓到，这处不会）。

**发现方式**：**真机只读验证**，不是单元测试。上一批的单测覆盖的是"下推发生"，没有覆盖"下推到哪一侧才成立"；
真机语句本意是构造保留侧的对照，却因为拒码文案而暴露了规则本身的来源不成立。

| 用例 | 钉住的判断 |
| ---- | ---------- |
| `a literal in ON may only reach a read the join is free to drop` | `INNER`/`LEFT` 上写之前表的字面量、`RIGHT` 上写本次引入表的字面量、`FULL` 上写任一侧的字面量 → 全部按名拒绝；并**行为断言** `RIGHT JOIN ... AND A.TRKORR = 'K1'` 的过滤器落在 **A 的读取**上（`calls[0].filters`）而 B 的读取不带过滤器（`calls[1].filters` 为空），且结果里 B 的未匹配行以 `A.TRKORR=""` 保留 |

## 9. 剩余风险

1. 本批修正**尚无真机确认**（见 §8）；单测覆盖的是服务端解析与下推路由，不是 SAP 侧读取行为。
2. `INNER` 上的字面量条件仍只接受"本次引入的表"，写到之前的表会被拒绝并提示移入 `WHERE`。这是**有意的收窄**（两者等价，保留一种写法），不是缺陷；但对 `RIGHT` 而言这种收窄不成立，故本批才必须按类型分叉。
3. `ON` 中"列 = 字面量"的 40 字符上界与 `WHERE` 一致；超界走 `return undefined`（保持平台原生错误），不新造拒绝码。
4. 三表混合（如 `A LEFT JOIN B ... RIGHT JOIN C ...`）时，本批规则按"该次联接丢得起哪一侧"判定，语义与两表情形一致；该组合无用例覆盖，属未验证范围。
